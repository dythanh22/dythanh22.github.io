6.1 Vì sao cần Triton — và không phải gì?

FastAPI + session.run() đã đủ production chưa — Triton thêm gì?

Quan trọngÝ chính

Triton biến nhiều artifact (onnx/plan/pt/py…) thành service có HTTP/gRPC, validation, batching, concurrency, multi-model, versioning, health, metrics. Nó không thay TensorRT hay ORT — nó serve chúng. frontend ≠ scheduler ≠ backend ≠ model instance.

Production cần thêm ngoài “chạy model”: endpoint, request validation, batching, concurrency, multi-model, versioning, health, metrics, rollout, GPU tuning.

Tự viết FastAPI thường phải tự lo parse → preprocess → H2D → runtime → batch thủ công → concurrent → versions → metrics → readiness → rollback.

Triton flow:

client → HTTP/gRPC → frontend → per-model scheduler
  → backend runtime → model instance → response
Công cụ Vai trò Liên quan Triton
ONNX IR / interchange Serve qua ORT backend
ONNX Runtime Chạy ONNX Có ORT backend
TensorRT Compiler/runtime NVIDIA Serve .plan
Triton Inference serving server Queue, batch, versions, metrics
Kubernetes Orchestration Deploy Triton pod
FastAPI Web generic Thiếu inference scheduler/batching chuyên dụng
vLLM / TRT-LLM LLM serving Có thể gắn như backend 
ONNX/TensorRT: how to execute efficiently.
Triton: how to serve that execution to many clients.
MẹoMental model 5 khối + multi-model

Client → Frontend → Model repository (model + config.pbtxt) → Per-model scheduler (batch/queue) → Backend → Model instances (GPU/CPU).

Mỗi model có scheduler/config/backend/instances riêng. Một server có thể đồng thời: image_classifier_trt (GPU0 + dynamic batch), text_embedding_onnx (GPU1), preprocess_python (CPU), llm_vllm (GPU2/3).

6.2 Architecture và request path

Request đi qua những lớp nào trước khi chạm GPU?

Quan trọngÝ chính

Path: client → frontend (parse/validate) → scheduler (default / dynamic / sequence / ensemble) → gán model instance → backend execute → validate output → metrics → response. Nhầm lẫn lớp sẽ debug sai chỗ (protocol vs queue vs kernel).

Lớp Việc
Frontend Protocol, model name/version, tensor metadata
Scheduler Khi nào chạy; có batch với request khác không
Backend Gọi TRT / ORT / PyTorch / Python / custom
Instance Execution slot thật trên CPU/GPU
MẹoScheduler types (tóm tắt đủ dùng)

Default: một request → một execution (không gom batch).
Dynamic batching: gom nhiều request thành batch server-side (Mục 6.6).
Sequence batching: stateful / sequence (ASR, một số RNN).
Ensemble: pipeline nhiều model steps — ensemble không có compute instance riêng; child models mới có.

6.3 Model repository

Vì sao repository là deployment interface quan trọng nhất của Triton?

Quan trọngÝ chính

Model repository = filesystem chứa artifact + config.pbtxt + version dirs. Layout sai → model không load. Tên thư mục = model name (trừ khi config set name). Production: package repository từ CI → container/artifact → deploy.

Layout chuẩn:

<model-repository-path>/
  <model-name>/
    config.pbtxt
    <version>/          # số nguyên: 1, 2, 3…
      <model-definition-file>

Ví dụ:

model_repository/
  tiny_classifier_onnx/
    config.pbtxt
    1/model.onnx
  tiny_classifier_trt/
    config.pbtxt
    1/model.plan
  normalize_python/
    config.pbtxt
    1/model.py
tritonserver --model-repository=/models

export RELEASE=26.04   # chỉnh theo NGC tag bạn dùng
docker run --gpus all --rm -it --net host \
  -v $PWD/model_repository:/models \
  nvcr.io/nvidia/tritonserver:${RELEASE}-py3 \
  tritonserver --model-repository=/models

Version directories: số nguyên tăng dần. version_policy quyết định version nào serve (ví dụ latest / specific). Client có thể request version cụ thể.

MẹoCI/CD package flow

train/export → validate → benchmark → package repository → push artifact/container → deploy Triton. Không sửa file “live” lung tung trên production filesystem (đặc biệt với poll mode — Mục 6.9).

6.4 config.pbtxt: trái tim deployment

max_batch_size > 0 thì dims có gồm batch dimension không?

Quan trọngÝ chính

config.pbtxt mô tả cách Triton load/serve model. Khi max_batch_size > 0, dims không gồm batch — request shape = [B] + dims. Khi max_batch_size: 0, dims = full shape (không batch ẩn). Tên I/O phải khớp artifact.

Config tối thiểu (ONNX):

name: "tiny_classifier_onnx"
backend: "onnxruntime"
max_batch_size: 8

input [
  {
    name: "input"
    data_type: TYPE_FP32
    dims: [ 1, 28, 28 ]
  }
]

output [
  {
    name: "logits"
    data_type: TYPE_FP32
    dims: [ 10 ]
  }
]
Field Ý nghĩa
name Nên trùng tên thư mục; set rõ cho đọc được
backend / platform Loại runtime; hiện đại đọc docs backend
max_batch_size Batch tối đa Triton được tạo; 0 = không batching
input/output name, data_type, dims khớp model
Artifact Khai báo thường gặp File
ONNX backend: "onnxruntime" model.onnx
TensorRT platform: "tensorrt_plan" model.plan
Python backend: "python" model.py
TorchScript backend: "pytorch" model.pt 
max_batch_size > 0:  request shape = [B] + config dims
max_batch_size = 0:  request shape = config dims

Ví dụ không batch:

max_batch_size: 0
input [{ name: "input" data_type: TYPE_FP32 dims: [ 1, 3, 224, 224 ] }]
Cảnh báoBẫy thường gặp

Export ONNX không đặt input_names/output_names → tên kiểu input.1, onnx::Gemm_23 → config dễ sai. Export nên đặt tên rõ + dynamic_axes cho batch.

MẹoExport ONNX thân thiện Triton 
torch.onnx.export(
    model, example_input, "model.onnx",
    input_names=["input"], output_names=["logits"],
    dynamic_axes={"input": {0: "batch"}, "logits": {0: "batch"}},
    opset_version=17,
)

6.5 Backends: TensorRT, ONNX, Python và khác

Khi nào serve .plan, khi nào serve .onnx, khi nào Python backend?

Quan trọngÝ chính

Backend = lớp biết execute artifact. TRT: perf cao, phụ thuộc GPU/version/profile. ORT: dễ/portable hơn. Python: preprocess/postprocess linh hoạt nhưng dễ bottleneck. LLM: vLLM / TensorRT-LLM như backend riêng (Lesson 9).

Backend Artifact Ưu Nhược
TensorRT model.plan Latency/throughput tốt; fusion/tactics/precision Portability; profiles; build phức tạp
ONNX Runtime model.onnx Dễ deploy; CPU/GPU Có thể chậm hơn TRT; fallback EP
PyTorch model.pt Gần training stack Thường không tối ưu bằng TRT
Python model.py Pre/post, glue logic GIL/CPU; dễ thành bottleneck pipeline
DALI / FIL / vLLM / TRT-LLM theo docs Pipeline data / tabular / LLM Cần hiểu workload riêng

TensorRT config tối thiểu:

name: "resnet50_trt"
platform: "tensorrt_plan"
max_batch_size: 32
input [{ name: "input" data_type: TYPE_FP32 dims: [ 3, 224, 224 ] }]
output [{ name: "logits" data_type: TYPE_FP32 dims: [ 1000 ] }]

Plan compatibility: build trên đúng GPU arch + TensorRT/CUDA của môi trường deploy (Lesson 4). Dynamic batching phải khớp optimization profiles — max_batch_size Triton không được vượt max profile.

Python backend khi nào: preprocess/postprocess, feature engineering nhẹ, glue không có backend native. Tránh logic nặng trên critical path nếu GPU model đã nhanh.

MẹoProtocols và client

Triton expose HTTP (thường :8000), gRPC (:8001), metrics (:8002). Client: tritonclient Python (HTTP/gRPC), Perf Analyzer. gRPC thường tốt hơn cho binary tensor throughput cao; HTTP tiện debug. KServe/V2 inference protocol là chuẩn API.

6.6 Dynamic batching deep dive

Vì sao throughput tăng nhưng p99 có thể xấu — và preferred_batch_size khi nào dùng?

Quan trọngÝ chính

Dynamic batching gom nhiều request (thường batch-1) thành batch lớn hơn server-side. Có ích khi traffic dày, model batchable, GPU chưa saturate ở batch 1, SLO cho phép queue delay. Tune theo SLO (p99), không chỉ throughput. Bắt đầu dynamic_batching { } — không set preferred_batch_size mặc định nếu chưa có bằng chứng benchmark.

Ví dụ số:

Batch 1 latency: 3 ms  →  8 request riêng: 8×3 = 24 ms GPU time
Batch 8 latency: 8 ms  →  1 batch: 8 ms GPU time

Throughput tăng; mỗi request có thể thêm queue delay.

Có ích khi Ít ích khi
Nhiều request batch-1 Traffic thấp
GPU chưa saturate Model không batch / shape lệch nhiều
SLO cho phép delay nhỏ Pre/post là bottleneck; p99 quá chặt
Compute giảm tương đối khi batch↑ Client đã gửi batch lớn; LLM cần continuous batching 
max_batch_size: 32

dynamic_batching { }

# hoặc có delay:
dynamic_batching {
  max_queue_delay_microseconds: 100
}

# chỉ khi benchmark chứng minh batch 4/8/16 đặc biệt tốt:
dynamic_batching {
  preferred_batch_size: [ 4, 8, 16 ]
}
Tham số Ý nghĩa
max_batch_size Batch tối đa; quá lớn → latency/memory/profile spike
max_queue_delay_microseconds Giữ request chờ thêm peer; dài hơn → batch lớn hơn, p99 rủi ro hơn
preferred_batch_size Ưu tiên các batch “ngon”; không đặt mặc định

Shape compatibility: [1,3,224,224]×N có thể batch; 224 vs 256 vs 384 khó — cần resize/pad, bucket, tách endpoint, hoặc kiểm soát dynamic shape.

Trade-off p99 (ví dụ):

Without batching:  p50=8ms  p99=20ms   thr=300 rps
With dyn batch:    p50=12ms p99=80ms   thr=1100 rps

SLO p99 < 100ms → có thể OK. SLO p99 < 30ms → thất bại dù thr cao.

MẹoBốn khái niệm dễ nhầm
  1. Client concurrency — số client đồng thời
  2. Client batch size — batch mỗi request client gửi
  3. Dynamic batch size — batch Triton gom server-side
  4. Instance count — số execution slot song song

Đừng nhầm “client gửi batch=8” với “dynamic batching đang hoạt động”.

6.7 instance_group và concurrent execution

Tăng count khi nào giúp — khi nào hại?

Quan trọngÝ chính

Model instance = execution slot. Dynamic batching gom request; nhiều instances chạy song song. Tăng count hữu ích khi một instance chưa saturate GPU / nhiều concurrent / model nhỏ. Hại khi model lớn (VRAM), GPU đã full, hoặc contention.

instance_group [
  { count: 2 kind: KIND_GPU }
]

# chỉ định GPU:
instance_group [
  { count: 1 kind: KIND_GPU gpus: [ 0 ] },
  { count: 2 kind: KIND_GPU gpus: [ 1 ] }
]

instance_group [
  { count: 2 kind: KIND_CPU }
]
model: resnet50_trt
  instance 0 → GPU 0
  instance 1 → GPU 0
  instance 2 → GPU 1

Tune cùng dynamic batching: benchmark matrix (batch delay × instance count × concurrency) — không chỉnh một nút theo cảm tính.

Python backend (preprocess)

model_repository/normalize_python/config.pbtxt + 1/model.py
name: "normalize_python"
backend: "python"
max_batch_size: 8
input [{ name: "INPUT" data_type: TYPE_UINT8 dims: [ 3, 224, 224 ] }]
output [{ name: "OUTPUT" data_type: TYPE_FP32 dims: [ 3, 224, 224 ] }]
import numpy as np
import triton_python_backend_utils as pb_utils

class TritonPythonModel:
    def initialize(self, args):
        self.mean = np.array([0.485, 0.456, 0.406], np.float32).reshape(1, 3, 1, 1)
        self.std = np.array([0.229, 0.224, 0.225], np.float32).reshape(1, 3, 1, 1)

    def execute(self, requests):
        responses = []
        for request in requests:
            x = pb_utils.get_input_tensor_by_name(request, "INPUT").as_numpy()
            x = x.astype(np.float32) / 255.0
            y = (x - self.mean) / self.std
            responses.append(
                pb_utils.InferenceResponse(
                    output_tensors=[pb_utils.Tensor("OUTPUT", y.astype(np.float32))]
                )
            )
        return responses

Python dễ bottleneck nếu: loop thay NumPy, copy nhiều, decode image nặng trên critical path. Cân nhắc DALI, client-side preprocess, hoặc fuse vào graph. Dùng khi logic nhẹ / prototype; tránh khi p99 cực thấp hoặc thr rất cao.

Ensemble pipeline

RAW_IMAGE → preprocess_python → classifier_trt → postprocess_python → LABEL

Ensemble không có compute instance — child models mới có. Cẩn shape/name mapping và Python bottleneck.

MẹoEnsemble config.pbtxt đầy đủ (concept)

input [{ name: "RAW_IMAGE" data_type: TYPE_UINT8 dims: [ 3, 224, 224 ] }]

ensemble_scheduling {
  step [

      model_name: "preprocess_python"

    },

      input_map { key: "input" value: "PREPROCESSED" }
      output_map { key: "logits" value: "LOGITS" }
    },
    {
      model_name: "postprocess_python"
      model_version: -1

6.8 Serving ONNX vs TensorRT trong Triton

Bắt đầu ORT hay TRT — và plan phải khớp profile thế nào?

Quan trọngÝ chính

Bắt đầu ORT cho correctness/portability; chuyển TRT khi profiling chứng minh ORT không đủ. Plan phải build trên target GPU/TRT/CUDA. max_batch_size Triton ≤ max của optimization profile. Engine không portable tuyệt đối (Lesson 4).

Chọn ORT khi Chọn TRT khi
Deploy nhanh, đang experiment Latency/throughput GPU critical
ONNX đã validate Architecture hỗ trợ TRT tốt
Perf đã đủ SLO Benchmark thấy lợi rõ + CI build engine 
Start with ONNX Runtime → Move to TensorRT when profiling proves need.
MẹoTRT + dynamic batching

Build: trtexec --onnx=... --fp16 --minShapes=... --optShapes=... --maxShapes=... --saveEngine=model.plan. Đặt Triton max_batch_size trong range profile. Sai profile → runtime shape error dù trtexec local OK trên máy khác.

6.9 Model management, observability và rollout

poll mode có nên là mặc định production không?

Quan trọngÝ chính

Control modes: none (load hết lúc start, immutable — thường tốt production đơn giản), explicit (load có chọn + API), poll (theo dõi filesystem — rủi ro partial update). Health: /v2/health/live vs /ready. Metrics :8002/metrics — tách queue duration vs compute infer duration. Prefer immutable deploy hoặc explicit; tránh poll mặc định.

Mode Hành vi Khi dùng
none Load all lúc start; ignore FS changes Prod đơn giản, immutable repo/pod
explicit Load theo --load-model + API Nhiều model, on-demand, controlled reload
poll Poll repo định kỳ Chỉ khi atomic update được kiểm soát chặt

Safer rollout: build → validate schema → correctness → load test → perf baseline → package immutable → deploy pod → readiness → shift traffic dần → monitor p99/error/GPU/queue → rollback nếu SLO vỡ.

curl localhost:8000/v2/health/live
curl localhost:8000/v2/health/ready
curl localhost:8002/metrics
Metric group Đọc gì
Request success/fail Error rate
Queue duration Serving/scheduler bottleneck
Compute infer duration Model/backend time
GPU util / memory Saturation vs OOM risk
Batch size (nếu có) Dynamic batch có gom không

  httpGet: { path: /v2/health/live, port: 8000 }

6.10 Perf Analyzer, Model Analyzer và debug

Perf Analyzer khác Model Analyzer — và debug batching “không chạy” bắt đầu từ đâu?

Quan trọngÝ chính

Perf Analyzer = load có kiểm soát để đo thr/latency/p99. Model Analyzer = explore config (instance, batch…) tự động hơn. Benchmark matrix: concurrency × batch × config. Đừng tối ưu thr mà bỏ p99/queue/GPU mem. Hầu hết lỗi thuộc: load fail, shape mismatch, batching off, p99 xấu sau batch, util thấp, VRAM cao, plan không tương thích.

# ví dụ — chỉnh model/shape theo lab
perf_analyzer -m tiny_classifier_onnx -u localhost:8000 \
  --concurrency-range 1:16 --shape input:1,1,28,28

perf_analyzer -m tiny_classifier_onnx \
  --concurrency-range 1:32 --measurement-interval 10000

Đừng nhầm client batch với dynamic batch. Matrix gợi ý: concurrency {1,4,16,64} × configs {no batch, dyn default, delay 100µs, instances 1/2}.

Vẽ throughput curve vs concurrency; tìm điểm GPU saturate / p99 vượt SLO.

Triệu chứng Kiểm tra đầu
Model không load Log Triton; path file; config.pbtxt; backend; I/O names; plan/CUDA version
Shape mismatch max_batch_size vs dims; client gửi [B]+dims đúng chưa
Dyn batch “không chạy” max_batch_size>0? có dynamic_batching? shapes compatible? traffic đủ?
p99 xấu sau batch Giảm delay / max batch; tăng instances; so SLO
Thr thấp + GPU util thấp Pre/post CPU? copy? concurrency thấp? Python bottleneck?
GPU memory cao Giảm instances / max batch; engine profile
Plan fail trong Triton nhưng trtexec OK GPU/TRT version khác; filename model.plan; input names

Debug checklists đầy đủ

Model không load: layout → version là số nguyên → filename convention → config.pbtxt syntax → backend/platform → I/O names/dtypes/dims → TRT compatibility → plugins.

Shape mismatch (hay nhất): quên rằng khi max_batch_size > 0, dims không gồm batch. Đúng: max_batch_size:32 + dims:[3,224,224]. Sai: dims:[1,3,224,224] cùng max_batch_size:32.

Dyn batch không chạy: max_batch_size>0? có block dynamic_batching? concurrency đủ? shapes compatible? model batchable? client đã gửi batch lớn + concurrency thấp? traffic thấp? quá nhiều instances “nuốt” request trước khi batch lớn? preferred_batch_size quá hẹp? delay quá nhỏ?

p99 xấu sau batch: queue duration↑? delay/max batch cao? preferred gây chờ? → hạ delay/max batch, bỏ preferred, thêm instance, hoặc tắt dyn batch cho endpoint latency-critical.

Thr thấp + GPU util thấp: concurrency thấp, network/JSON overhead, pre/post CPU, Python backend, H2D/D2H, gRPC vs HTTP.

VRAM cao: giảm instances / max batch; kiểm profile engine.

MẹoDesign patterns và anti-patterns

Patterns: (1) Single-model: ONNX→TRT plan→dyn batch→metrics. (2) Multi-model: gán GPU/instance theo SLO + memory plan. (3) Pipeline ensemble: Python→TRT→Python. (4) Low-latency: delay≈0, max batch nhỏ, TRT FP16/INT8, protocol nhanh. (5) High-throughput: max batch lớn, delay cao hơn, nhiều instance nếu VRAM cho phép.

Anti-patterns: copy config internet mù; preferred_batch_size không benchmark; tăng instance đến đầy VRAM; Python backend cho mọi thứ; chỉ đo mean latency; bỏ qua queue duration; poll mode + sửa file không atomic; giả định plan portable mọi GPU.

MẹoProduction checklist đầy đủ

Artifact: baseline accuracy+latency; I/O schema; TRT/ORT/CUDA/driver/GPU recorded.
Repository: layout; config khớp names/dims; version policy; warmup.
Runtime: live/ready; metrics (queue vs compute); batch+instances vs p99 SLO.
Deploy: immutable image/repo; canary; rollback; monitor error + GPU mem + thr.

class TinyCNN(nn.Module):

        super().__init__()
