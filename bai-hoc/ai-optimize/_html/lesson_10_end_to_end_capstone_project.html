10.1 Phạm vi, mục tiêu và chọn workload

Capstone này “làm gì đủ” và khi nào nên chọn CNN mặc định thay vì nhảy thẳng sang LLM?

Quan trọngÝ chính

Track mặc định là image classification (ResNet-50 hoặc MobileNetV3) vì đủ nhỏ để lặp nhanh mà vẫn bao phủ full pipeline production. LLM là nhánh mở rộng — không thay deliverable chính trừ khi bạn đã hoàn thành Track A tới Level 6+.

error rate: < 0.1%
correctness: top-1 consistent with baseline ≥ 99% sampled

Không có SLO → không biết “tối ưu đủ chưa”.

10.2 Kiến trúc, contract và deliverables

Service production cần những thành phần nào — và artifact nào phải bàn giao?

Quan trọngÝ chính

Kiến trúc mục tiêu là Client → (optional FastAPI gateway) → Triton → ORT và/hoặc TensorRT → GPU → metrics. Deliverable không chỉ là .onnx/.plan mà là repo scripts + configs + reports + ops chứng minh service vận hành được.

So sánh runtime trong project:

Layer Artifact Vai trò
Baseline PyTorch eager / torch.compile Tham chiếu correctness
Intermediate ONNX Runtime CPU/CUDA Baseline portable
Optimized TensorRT FP16 .plan Production path chính
Optional TensorRT INT8 .plan Cost/latency nếu accuracy OK

Model contract (bắt buộc viết trước export):

input:  name=input, FP32, [N,3,224,224], NCHW, ImageNet normalize
output: name=logits, FP32, [N,1000]
pre: decode RGB → resize 256 → center crop 224 → normalize → NCHW
post: optional softmax → top-k → labels.txt

Bug production thường nằm ở preprocess/postprocess, không phải “weights sai”.

Notebook một file “chạy được trên máy tôi” ≠ production project. Capstone yêu cầu scripts đánh số, model repository, ops files và report tái tạo được.

10.3 Phase A–B: Export, validate và tối ưu (+ quant)

Làm sao đi từ weights PyTorch tới engine TensorRT mà không mang theo bug silent?

Quan trọngÝ chính

Thứ tự cứng: export → ONNX checker → so sánh logits PyTorch vs ORT → (optional onnxsim) → baseline ORT → trtexec FP16 với profile khớp traffic. Fail equivalence thì không build TensorRT. INT8 chỉ sau khi FP16 đạt SLO và accuracy gate.

Bước Việc Gate thoát
A1 Contract + chọn model Contract đã ghi; shape/dtype cố định
A2 torch.onnx.export (opset 17, dynamic batch) File .onnx tồn tại
A3 onnx.checker + inspect graph Checker OK
A4 Compare PyTorch vs ORT assert_allclose pass
A5 Optional onnxsim + re-validate Semantic vẫn OK
B1 ORT CPU/CUDA baseline Số liệu trong benchmark_report.md
B2 trtexec --fp16 + profiles Engine load + dumpProfile
B3 Optional INT8 Accuracy delta chấp nhận được

Dynamic batch chỉ ở dim 0; H/W cố định 224 để giảm phức tạp profile. Profile gợi ý: min=1, opt=8, max=32 — khớp dynamic batching Triton, không max=1024.

MẹoScripts Phase A–B (export / validate / compare / ORT bench / trtexec)

Export (scripts/01_export_to_onnx.py):

import argparse
from pathlib import Path
import torch
import torchvision.models as models

def export_resnet50(output_path: str, dynamic_batch: bool = True) -> None:
    model = models.resnet50(weights=models.ResNet50_Weights.DEFAULT)
    model.eval()
    dummy_input = torch.randn(1, 3, 224, 224)
    dynamic_axes = None
    if dynamic_batch:
        dynamic_axes = {"input": {0: "batch"}, "logits": {0: "batch"}}
    torch.onnx.export(
        model, dummy_input, output_path,
        export_params=True, opset_version=17, do_constant_folding=True,
        input_names=["input"], output_names=["logits"],
        dynamic_axes=dynamic_axes,
    )
    print(f"Exported ONNX model to: {output_path}")

def main() -> None:
    parser = argparse.ArgumentParser()
    parser.add_argument("--output", default="models/resnet50_onnx/1/model.onnx")
    parser.add_argument("--static-batch", action="store_true")
    args = parser.parse_args()
    Path(args.output).parent.mkdir(parents=True, exist_ok=True)
    export_resnet50(args.output, dynamic_batch=not args.static_batch)

if __name__ == "__main__":
    main()
python scripts/01_export_to_onnx.py --output models/resnet50_onnx/1/model.onnx

trtexec build (05_build_engine_trtexec.sh):

#!/usr/bin/env bash
set -euo pipefail
ONNX_MODEL="${1:-models/resnet50_onnx/1/model.onnx}"
ENGINE_OUTPUT="${2:-models/resnet50_trt/1/model.plan}"
mkdir -p "$(dirname "$ENGINE_OUTPUT")"
trtexec \
  --onnx="$ONNX_MODEL" --saveEngine="$ENGINE_OUTPUT" \
  --minShapes=input:1x3x224x224 \
  --optShapes=input:8x3x224x224 \
  --maxShapes=input:32x3x224x224 \
  --fp16 --workspace=4096 \
  --profilingVerbosity=detailed --dumpLayerInfo --dumpProfile

Flags cần hiểu: --onnx, --saveEngine, min/opt/max shapes, --fp16, --workspace, dump profile/layer. Profile xấu: min=1,opt=1,max=1024. Profile tốt khớp serving: 1/8/32.

Validate engine:

trtexec --loadEngine=models/resnet50_trt/1/model.plan \
  --shapes=input:1x3x224x224 --warmUp=500 --duration=30 \
  --iterations=1000 --dumpProfile
# lặp với shapes ...:8x3x224x224

Ghi: Throughput, Latency, Enqueue, H2D, GPU Compute, D2H.

Symptom trtexec Nghĩa thường gặp
GPU Compute cao Bottleneck model
H2D / D2H cao Transfer / preprocess
Enqueue cao CPU schedule / launch nhỏ
Throughput thấp, latency thấp Concurrency/batch thấp
p99 ≫ p50 Queue / contention / cold path

INT8 extension: calibration dataset → cache/QDQ → INT8 engine → validate accuracy → bench → bảng Precision comparison (Runtime | Precision | p99 | Throughput | Accuracy delta | Decision). Chỉ accept nếu latency/throughput↑ và accuracy/stability OK.

10.4 Phase C–D: Deploy Triton và benchmark

Engine nhanh với trtexec — làm sao chứng minh Triton + API cũng đạt SLO?

Quan trọngÝ chính

Serve cả hai backend (resnet50_onnx + resnet50_trt) để so sánh công bằng. Benchmark hai lớp: Perf Analyzer → Triton trực tiếp (model/server) và load test → gateway → Triton (E2E). Mục tiêu là tìm knee: concurrency trước khi p99 phá SLO.

config.pbtxt phải khớp artifact — không đoán tên I/O:

Field ONNX backend TensorRT backend
name resnet50_onnx resnet50_trt
backend/platform backend: "onnxruntime" platform: "tensorrt_plan"
max_batch_size 32 32 (≤ profile max)
input dims [3,224,224] FP32 giống
output dims [1000] FP32 giống
dynamic_batching max_queue_delay_microseconds: 1000 giống
instance_group count: 1, KIND_GPU giống
Mistake config Hệ quả
Sai input/output name Request fail
Sai dims / dtype Shape mismatch
max_batch_size lệch profile TRT Runtime error batch lớn
Sai backend/platform Model load fail

Health: /v2/health/live, /v2/health/ready; metadata models; metrics :8002/metrics.

Phân rã latency:

client latency ≈ network + queue + input + compute infer + output + transfer
Symptom Triton Bottleneck Action
Queue time cao Overload / batch delay Giảm concurrency, thêm instance, tune batch
Compute infer cao Model/GPU TRT/precision/model nhỏ hơn
Input/output cao Pre/post / copy Tối ưu preprocess, giảm output
GPU util thấp, latency cao CPU/client Profile gateway
GPU util cao, p99 cao Saturation Scale out / giảm delay
p50 tốt, p99 xấu Queue / noisy neighbor Buffer capacity, isolate
Cảnh báoBẫy thường gặp

Gateway latency ≠ model latency. Triton TRT 5 ms nhưng API p99 90 ms → bottleneck ngoài engine (decode, Python, network, queue). Đo cả hai lớp.

10.5 Phase E–F: Monitoring, rollout và vận hành

Service đã đạt số trên lab — làm sao đưa vào traffic thật mà vẫn rollback trong vài phút?

Quan trọngÝ chính

Ops bắt đầu trước khi mở traffic: Prometheus scrape, alert actionable, Docker Compose (rồi K8s), shadow → canary 1→10→50→100% với gate, rollback triggers đã test, và runbook cho latency / error / quality. Canary ≠ A/B.

Dashboard tối thiểu: request rate, error rate, p50/p95/p99, queue duration, compute infer, GPU util/mem, model name/version, instance count.

Strategy Mục tiêu Khi dùng
Shadow So sánh v2 không ảnh hưởng user Trước canary
Canary An toàn, rollback nhanh Mặc định production
A/B Đo business/quality impact Ranking/LLM/moderation…

Shadow metrics: top-1 match, top-5 overlap, KL (optional), latency/error v1 vs v2. Không log raw user data nếu policy không cho.

K8s: readinessProbe = nhận traffic; livenessProbe = restart; startupProbe = engine load chậm. HPA theo CPU thường không đủ cho GPU — ưu tiên queue/pending/RPS/replica (custom metrics / KEDA). Scale out khi queue cao vài phút; scale in chậm; giữ capacity buffer.

ops/alert_rules.yml (ý tưởng): InferenceHighErrorRate — failure/success > 0.01 for 10m (page); InferenceHighQueueTime — avg queue > 50 ms (warning); InferenceHighComputeLatency — avg compute infer > 50 ms (warning). Alert phải actionable.

Docker Compose: triton (GPU, ports 8000–8002, mount models, strict config) + prometheus (yml + alert_rules) + grafana:3000. Cần NVIDIA Container Toolkit.

K8s Deployment: 1× nvidia.com/gpu; args tritonserver --model-repository=/models --strict-model-config=true; readiness /v2/health/ready; liveness /v2/health/live; startupProbe dài cho engine lớn; PVC mount /models. Service expose 8000/8001/8002.

HPA: minReplicas 1, maxReplicas 5. CPU utilization 70% chỉ là skeleton — production ưu tiên queue duration / pending requests / RPS/replica (custom metrics hoặc KEDA). Scale out khi queue cao vài phút; scale in chậm; giữ capacity buffer.

Rollout plan (ops/rollout_plan.md) pre-flight: ONNX OK; TRT OK; PyTorch↔︎ONNX; ONNX↔︎TRT; offline accuracy; Perf Analyzer; p99 in SLO; dashboard; rollback artifact.

Stages: Shadow → Canary 1% → 10% → 50% → 100% (mỗi bậc: no SLO violation, no alert, no quality regression).
Rollback triggers: error↑, p99↑, GPU OOM, quality↓, crash loop, queue↑, user-visible incident.
Procedure: stop v2 → 100% v1 → verify recover → freeze → incident review.

Shadow:

prod request → v1 = real response
            → v2 = copy; log/compare only

So sánh: top-1 match, top-5 overlap, KL optional, latency/error. Không log raw PII.

def compare_topk(logits_v1, logits_v2, k=5):
    top_v1 = set(logits_v1.argsort()[-k:])
    top_v2 = set(logits_v2.argsort()[-k:])
    return len(top_v1 & top_v2) / k

A/B ≠ canary: canary = safety; A/B = sticky bucketing + primary metric + guardrails + statistical power + duration. Ví dụ INT8 vs FP16; primary = completion rate; guardrails = p99, error, human sample. Classification API ít cần A/B; ranking/LLM/moderation thì trung tâm.

10.6 Cost, báo cáo cuối và rubric

Tối ưu “đủ” nghĩa là gì khi nhìn cost, PRR và Level tự đánh giá?

Quan trọngÝ chính

Cost không chỉ là GPU-giờ tại peak throughput — phải tính operating point đạt SLO + idle buffer + HA + gateway + observability. Final report + production readiness review biến số liệu thành quyết định (demo / staging / limited / full production). Aim Level 6+.

Công thức cơ bản:

\[ \text{cost per 1M} = \frac{\text{hourly GPU cost}}{\text{sustained inferences/hour}} \times 10^{6} \]

Ví dụ: $2/h, 500 req/s → 1.8M req/h → $1.11 / 1M. Production còn idle buffer, replication, gateway, logging, egress, on-call.

10.7 Failure modes và mental models cả khóa

Khi capstone “gãy”, bạn debug theo giả thuyết nào — và nhớ lại mantra gì từ Lesson 1–9?

Quan trọngÝ chính

Hầu hết failure modes là mismatch (export/eval, config vs artifact, trtexec vs Triton, mean vs p99) chứ không phải “TensorRT hỏng”. Mental model xuyên suốt: artifact ≠ service; tối ưu phải validate correctness; config.pbtxt là production code; benchmark phải trả lời quyết định SLO.

Failure Symptoms Causes điển hình Fix
ONNX “OK” nhưng sai Checker pass, pred lệch PyTorch train mode, opset, preprocess eval(), compare, đổi opset
TRT build fail Unsupported op, shape/profile Dynamic unbounded, plugin Simplify, replace op, ORT fallback
Triton load fail Unavailable, config/backend error Sai name/dims, engine GPU mismatch Logs, metadata, rebuild cùng env
trtexec nhanh, Triton chậm p99 xấu Queue, batch delay, gateway, instances Perf Analyzer + tune queue/instances
p99 ≫ p50 10 ms vs 200 ms Burst, contention, cold, autoscale lag Buffer capacity, đừng chạy max throughput

Mental models mang theo sau khóa:

model artifact ≠ inference service ≠ monitored ≠ reliable
mean latency tốt vẫn có thể phá UX nếu p99 xấu
TensorRT phải verify: correctness, accuracy, latency, throughput, memory, compatibility
config.pbtxt đổi batching / shapes / instances / backend / version_policy → coi như code
Benchmark hỏi: "Concurrency nào đạt p99 < 100 ms và RPS an toàn?" — không chỉ "model nhanh bao nhiêu?"
Ops trước deploy: no metrics → no diagnosis; no rollback → risky; no SLO → no reliability

Model correctness: export eval; I/O documented; checker; PyTorch↔︎ONNX; ONNX↔︎TRT; preprocess/postprocess tests; labels versioned.

Summary

  • Capstone = full loop: export → validate → optimize → serve → bench → monitor → canary → cost/report — không dừng ở “infer local”.
  • Track A (CNN + Triton) là deliverable chính; LLM là extension sau Level 6.
  • Gates cứng: equivalence trước TRT; config khớp artifact; dual-backend so sánh; hai lớp benchmark; knee trước khi chọn concurrency.
  • Ops là một nửa điểm: metrics/alerts, shadow/canary, runbook, probes, cost tại operating point đạt SLO.
  • Rubric Level 6+; PRR biến engineering thành quyết định vận hành.
Serve under SLO, with evidence — not just maximize throughput on a quiet GPU.
