9.1 Vì sao LLM inference khác classic serving?

Image classifier tối ưu một forward pass — vì sao serve LLM buộc phải nghĩ theo token, KV cache và nhiều bước decode?

Quan trọngÝ chính

Classic inference gần như một request = một forward = một output cố định. LLM decoder-only là một request = prefill + vòng decode autoregressive, output length không biết trước, memory KV cache tăng theo context, và UX phụ thuộc TTFT cùng ITL chứ không chỉ E2E latency trung bình.

Chiều Classic (CNN / classifier) LLM inference
Forward / request Thường 1 Prefill + nhiều decode step
Output size Cố định / gần cố định Biến động theo max_tokens / EOS
Batching Gom request dễ hơn Output length lệch → static batch lãng phí
Memory nóng Weights + activation tạm Weights + KV cache per request
Bound điển hình Compute (model lớn) Prefill: compute-heavy; decode: memory-bandwidth
Metric chính Latency / RPS TTFT, ITL/TPOT, tokens/s, goodput
UX Chờ full response Streaming từng token

Ví dụ classic: image [1,3,224,224] → CNN → logits [1,1000].
Ví dụ LLM: prompt "Explain TensorRT in simple terms." → tokenize → prefill → token₁, token₂, … → stream.

Cảnh báoBẫy thường gặp

Đo “model latency” như một con số duy nhất cho LLM. Cùng mean E2E, một service có thể TTFT 2 s + ITL giật — UX tệ — trong khi service khác TTFT 300 ms + ITL mượt lại được coi là “chậm hơn” nếu chỉ nhìn average.

MẹoMental model decoder-only + ba loại memory

Ở mỗi layer:

Q = X Wq;  K = X Wk;  V = X Wv
Attention(Q, K, V) = softmax(QKᵀ / √d) V

Token mới attend tới mọi token trước (1..t). Không cache thì mỗi decode step tính lại K/V cho cả prefix — cực kỳ lãng phí.

Loại Vai trò Tính chất
Weights “Kiến thức” model Gần như static sau load
Activations Giá trị tạm một forward Sống ngắn
KV cache K/V đã tính cho token cũ Per-request, mọc theo sequence length 
Compute K/V once → store → next step chỉ tính K/V token mới → reuse cache

9.2 Prefill, decode và KV cache

Prefill tạo gì, decode tốn gì — và làm sao ước lượng KV cache trước khi OOM?

Quan trọngÝ chính

Prefill xử lý cả prompt một lần: tạo logits token đầu + KV cho prompt — thường compute-heavy, quyết định phần lớn TTFT. Decode mỗi bước gần như input length = 1 nhưng attention length = toàn bộ cache — thường memory-bandwidth-bound, quyết định ITL. KV cache thường làm capacity “hết chỗ” trước khi weights hết chỗ.

Phase Input vào model Việc chính Bound thường gặp Metric gắn
Prefill Toàn bộ prompt (vd. 2048 tokens) Hidden states, first logits, KV prompt Compute-heavy TTFT
Decode 1 token mới / step Next token + cập nhật KV Memory-bandwidth ITL / TPOT

Công thức đơn giản:

\[ \text{E2E} \approx \text{TTFT} + \text{generation\_time} \]

\[ \text{ITL} \approx \frac{\text{E2E} - \text{TTFT}}{N - 1} \]

(với \(N\) output tokens; tool benchmark có thể định nghĩa hơi khác — luôn ghi rõ công thức khi so sánh.)

Ước lượng KV cache (một request):

\[ \text{KV bytes} = L \times S \times 2 \times H_{\text{kv}} \times d_{\text{head}} \times b \]

Ký hiệu Ý nghĩa
\(L\) num_layers
\(S\) sequence_length (prompt + generated đã có)
\(2\) K và V
\(H_{\text{kv}}\) num_kv_heads
\(d_{\text{head}}\) head_dim
\(b\) bytes/element (FP16/BF16 = 2, FP8 = 1)

Ví dụ: \(L{=}32\), \(H_{\text{kv}}{=}8\), \(d{=}128\), \(b{=}2\), \(S{=}4096\) → \(\approx 512\) MB / request. 64 request đồng thời ≈ 32 GB chỉ cho KV — đó là lý do serving LLM thường bị giới hạn bởi KV trước weights.

MẹoCon số cụ thể: MQA/GQA và checklist TTFT/ITL

MQA / GQA giảm \(H_{\text{kv}}\) so với MHA cổ điển (num_query_heads > num_kv_heads). Ví dụ MHA 32 KV heads → GQA 8 heads: KV ≈ 1/4 nếu các thông số khác giữ nguyên.

TTFT tăng khi: prompt dài, queue dài, batch prefill quá lớn, GPU bận, prefix cache miss, tokenizer chậm, TP/PP chưa tốt.

ITL xấu khi: decode batch nhỏ, KV dài, memory bandwidth bottleneck, prefill chen decode, scheduler không ưu tiên decode, preemption / network buffer.

request sent
  | tokenization + queue + prefill
  v
first token  ← TTFT
  | decode steps…
  v
last token   ← E2E latency

9.3 Continuous batching và scheduling

Static batching từng “thắng” với CNN — vì sao với LLM decode loop nó không còn đủ?

Quan trọngÝ chính

Continuous batching (còn gọi in-flight batching / iteration-level batching) coi batch là tập sequence đang active ở mỗi iteration, không phải nhóm cố định chạy tới khi mọi request xong. Request ngắn không bị kẹt chờ request dài; GPU tận dụng decode step vốn nhỏ — đổi lấy scheduler và memory manager phức tạp hơn.

Kiểu Cách hoạt động Điểm yếu với LLM
Static batching Gom A,B,C,D → chạy tới khi tất cả xong Request ngắn chờ dài; slot idle; throughput kém khi output lệch
Dynamic batching Chờ ≤ X ms rồi chạy batch Vẫn hữu ích cho prefill; chưa giải quyết generation length lệch
Continuous / IFB Mỗi step: thêm/bớt sequence khi còn capacity Cần KV paging + fairness + metric tốt 
t1: batch [A, B, C]
t2: A done, add D → [B, C, D]
t3: add E (prefill) while B/C/D decode → [B, C, D, E]

Ý tưởng cốt lõi: Batch is not a fixed group of requests — it is a changing set of active sequences at each iteration.

Lợi ích Trade-off
GPU utilization cao hơn Scheduler phức tạp
Request mới ít chờ hơn Cấp phát/thu hồi KV liên tục
Phù hợp streaming Fairness / tail latency khó hơn
Tăng output token throughput Dễ tối ưu TPS mà phá UX nếu thiếu metric

Chunked prefill: chia prompt dài thành chunk để xen kẽ với decode — tránh “một prefill dài làm ITL toàn batch xấu”.

Knob liên quan Hướng ảnh hưởng thường gặp
max_num_batched_tokens nhỏ hơn ITL thường tốt hơn
max_num_batched_tokens lớn hơn TTFT / prefill throughput thường tốt hơn
Cảnh báoBẫy thường gặp

Tăng concurrency / batch token budget tối đa để “đầy GPU” rồi tuyên bố thắng vì system TPS cao — trong khi TTFT/ITL p99 và goodput (request thỏa SLO) giảm. Throughput thô ≠ UX.

MẹoĐào sâu: fairness, priority và mental model scheduler

Continuous batching làm fairness và tail latency khó kiểm soát hơn static batch. Production thường cần:

  • admission control / max queue
  • tách pool short-chat vs long-context / long-generation
  • ưu tiên decode để giữ stream mượt (chunked prefill hỗ trợ)
  • quota / rate limit theo tenant hoặc max_tokens
Scheduler mỗi iteration:
  chọn prefill jobs + decode sequences trong token budget
  cấp / thu hồi KV blocks
  emit tokens → stream

Không có “priority queue hoàn hảo” trong mọi engine — nhưng nguyên tắc ổn định: đừng trộn mọi length vào một pool duy nhất nếu p99 là SLO cứng.

9.4 PagedAttention và quản lý bộ nhớ KV

Vì sao reserve một tensor KV liên tục theo max_seq_len lại lãng phí — và PagedAttention sửa gì?

Quan trọngÝ chính

PagedAttention chia KV thành block/page cố định (ý tưởng virtual memory): cấp phát theo nhu cầu thật, giảm fragmentation, thu hồi khi request xong, và cho phép chia sẻ block khi nhiều request cùng prefix. Đây là serving-system design (block table + kernel đọc non-contiguous), không chỉ “struct dữ liệu đẹp”.

Contiguous reserve Paged KV
Đoán trước max length / request Cấp block khi sequence mọc
Waste nếu output ngắn Thu hồi block khi xong
Fragmentation vùng trống nhỏ Physical blocks không cần liền kề
Khó share prefix Share block khi prefix trùng

Ví dụ waste: ba request đều reserve 4096 nhưng dùng 512 / 3000 / 128 → phần lớn GPU memory “đứng yên”.

Engine cần: block table, map logical position → physical block, kernel layout tối ưu, scheduler ↔︎ memory manager phối hợp chặt.

MẹoPrefix caching / KV reuse — lợi ích và checklist miss

Nhiều traffic production chia sẻ system prompt, policy, RAG template, few-shot, một phần chat history. Cache hit → giảm prefill compute và TTFT; đặc biệt mạnh với prompt hệ thống dài, multi-turn, agent, RAG template.

Trade-off: hit phụ thuộc pattern; cần eviction; multi-tenant cần isolation/salt; prefix phải match đúng token-level (chat template / whitespace / special token).

Checklist khi prefix caching không hiệu quả:
[ ] Prefix giống nhau ở token level?
[ ] Chat template đổi whitespace / special token?
[ ] Request đầu đã xong trước khi request sau reuse?
[ ] Cache bị evict vì memory pressure?
[ ] Multi-tenant isolation/salt chặn share?
[ ] Block size quá lớn → ít block đủ điều kiện share?

9.5 Speculative decoding và parallelism

Làm sao giảm số forward decode đắt của model lớn — và khi nào phải shard sang nhiều GPU?

Quan trọngÝ chính

Speculative decoding dùng draft nhẹ đề xuất \(k\) token rồi target model verify một lần: lợi khi acceptance rate cao và decode đang memory-bound; có thể vô ích hoặc hại khi QPS đã bão hòa GPU, draft đắt, hoặc sampling quá ngẫu nhiên. Multi-GPU: TP shard tensor, PP chia layer, EP phân tán MoE experts — mỗi cái đổi memory/latency/communication trade-off.

Điều kiện thường có lợi Điều kiện thường ít lợi / hại
Low–medium QPS High QPS, GPU đã saturated
Target lớn, decode memory-bound Draft chiếm memory/compute lớn
Draft rẻ + acceptance cao Acceptance thấp
Output dài, latency/user quan trọng Output ngắn; sampling rất random
Overhead scheduler lớn
Biến thể Ý tưởng
Draft model Model nhỏ hơn sinh token nháp
N-gram speculation Pattern lặp trong context; không cần model phụ
EAGLE / EAGLE3 Speculator chuyên dụng
MTP Multi-token prediction
PARD / suffix / custom Tùy engine
Parallelism Việc làm Ghi nhớ
TP (tensor) Shard matrix ops qua GPU Giảm memory/GPU, tăng communication
PP (pipeline) Chia layer qua GPU Fit model lớn, thường tăng latency
EP (expert) Phân tán MoE experts Cho MoE; thêm chiều scheduling
Cảnh báoBẫy thường gặp

Bật speculative decoding rồi chỉ nhìn mean latency. Phải so off/on với cùng workload: TTFT, ITL p95/p99, output TPS, GPU memory, error rate, và chất lượng tương đương — kèm acceptance rate / draft latency.

MẹoĐào sâu: “không phải magic” và checklist khi không nhanh hơn 
Speculative decoding is not magic.
It is a latency optimization whose value depends on acceptance rate and workload.
[ ] Draft quá chậm?
[ ] Acceptance thấp?
[ ] High QPS đã saturate GPU?
[ ] Output quá ngắn?
[ ] Temperature/top_p làm dự đoán khó?
[ ] num_speculative_tokens quá nhiều hoặc quá ít?

Actions: thử nhiều draft length; n-gram/suffix nếu không muốn model phụ; tắt spec trên traffic high-QPS saturated nếu không lợi.

9.6 Serving stacks: vLLM, TensorRT-LLM và quantization LLM

Chọn vLLM để ship nhanh hay TensorRT-LLM để đẩy ceiling trên NVIDIA — tiêu chí thực dụng là gì?

Quan trọngÝ chính

vLLM tối ưu developer velocity: PagedAttention, continuous batching, OpenAI-compatible API, HF ecosystem, streaming/metrics. TensorRT-LLM tối ưu sâu trên NVIDIA GPU (kernel, IFB, paged KV, FP8/FP4/INT4 AWQ/SmoothQuant, multi-GPU). Chúng overlap nhưng không thay thế nhau hoàn toàn — workload đủ quan trọng thì benchmark cả hai. Quantization LLM (weights + thường cả KV) là đòn bẩy memory/throughput, không miễn phí về quality.

Tiêu chí vLLM TensorRT-LLM
Triết lý Serving linh hoạt, dễ dùng NVIDIA-optimized stack
Model ecosystem Rất mạnh với Hugging Face Model được hỗ trợ/tối ưu trên NVIDIA
API OpenAI-compatible phổ biến trtllm-serve / Triton, Dynamo, NIM…
Scheduler Continuous batching, PagedAttention In-flight batching, paged attention
KV PagedAttention, prefix caching Paged KV, reuse, offload/eviction
Quant Nhiều backend tùy model/HW FP8/FP4/INT4 AWQ/SmoothQuant sâu
Tuning effort Thấp → trung bình Trung bình → cao
Best fit Rapid production LLM serving Highly optimized NVIDIA production

Knobs ổn định hơn tên flag (tên có thể đổi theo version):

Concept Ảnh hưởng
max_model_len Context max → KV demand
max_num_seqs Active sequences; quá cao → memory pressure
max_num_batched_tokens Trade-off TTFT / ITL / throughput
gpu_memory_utilization Quá cao → dễ OOM
tensor_parallel_size / pipeline_parallel_size Fit model vs communication/latency
enable_prefix_caching Reuse prefix nếu traffic lặp
speculative_config Draft / n-gram / EAGLE / MTP…

Quantization thường gặp trên path LLM:

Kỹ thuật Mục tiêu chính
FP8 / FP4 (weights, KV, activation tùy path) Giảm memory, tăng throughput trên NVIDIA
INT8 SmoothQuant Activation/weight scale cho INT8
INT4 AWQ / GPTQ-style Nén weight mạnh; cần đánh giá quality
KV cache quantization Tăng số sequence active cùng VRAM
MẹoĐào sâu: khi nào chọn gì, multi-LoRA, Triton/NIM path

Chọn vLLM khi: cần HF → API nhanh; nhiều concurrent request; output length biến động; continuous batching + PagedAttention; multi-LoRA / structured outputs / tool-calling ecosystem; ưu tiên velocity.

Chọn TensorRT-LLM khi: NVIDIA GPU + team sẵn sàng tune; workload ổn định/đủ lớn; cần path FP8/FP4/INT4 tối ưu; multi-GPU/node; muốn NVIDIA production stack (Triton, Dynamo, NIM).

Dùng vLLM để học và triển khai nhanh là hợp lý.
Học TensorRT-LLM để hiểu performance ceiling và NVIDIA path.
Benchmark cả hai nếu workload đủ quan trọng.

Multi-LoRA / adapters: vLLM ecosystem hỗ trợ serve nhiều adapter trên cùng base — hữu ích khi nhiều tenant/task dùng chung backbone. Vẫn phải kế hoạch KV + rank memory và isolation.

Triton / NIM: TensorRT-LLM thường đi vào serving qua ecosystem NVIDIA; bài này không thay Lesson 6 — chỉ nhớ LLM backend vẫn cần metric token-level và rollout an toàn (Lesson 8).

Hugging Face TGI không phải trọng tâm nguồn bài này; trong thực tế team thường so TGI với vLLM theo API/ops preference — nguyên tắc đo (TTFT/ITL/TPS/goodput) giữ nguyên.

9.7 Production ops: streaming, metric token-level và quan sát

Throughput cao nhưng user thấy chậm — metric nào chứng minh service LLM “ổn”?

Quan trọngÝ chính

Streaming giảm perceived latency nhưng không miễn phí (chunk/SSE, detokenize lặp, connection dài). Đo LLM bằng TTFT, ITL/TPOT, E2E, per-user vs system TPS, kèm phân phối input/output length. RPS một mình gây hiểu nhầm. Goodput (throughput thỏa SLO) gần production hơn raw TPS.

Metric Định nghĩa ngắn Dùng để
TTFT Thời điểm first token − request sent Cảm nhận “bắt đầu trả lời”
ITL / TPOT Thời gian giữa các output token Độ mượt stream / decode
E2E Final token − request sent Tổng thời gian hoàn tất
Per-user TPS Output tokens user / generation_time UX một phiên
System TPS Tổng output tokens / wall time Capacity máy chủ
RPS Completed requests / s Chỉ kèm length distribution
Goodput Request thỏa SLO / s (hoặc tokens thỏa SLO) Đánh giá production

TTFT thường gồm: network, queue, tokenize, prefill, first decode, detokenize, streaming overhead.

Streaming trade-off:

small chunks → responsive, overhead cao
large chunks → efficient, UX kém mượt hơn

Một service có thể system TPS cao nhưng UX tệ nếu TTFT cao, ITL p99 cao, hoặc stream giật cụm lớn.

Ví dụ good: TTFT < 1000 ms, ITL p95 < 80 ms/token, E2E < 20 s, no error.

9.8 Playbook: bottleneck, cost, checklist và lựa chọn kiến trúc

Khi TTFT/ITL xấu hoặc OOM — nhìn đâu trước, và cost/1M tokens tính thế nào dưới SLO?

Quan trọngÝ chính

Capacity LLM bị ràng buộc bởi ba thứ cùng lúc: throughput (tokens/s tại SLO), KV memory, và latency SLO (TTFT/ITL). Cost nên theo tokens (input và output), không theo RPS. Debug theo triệu chứng → nguyên nhân → kiểm tra → hướng xử lý; checklist trước launch quan trọng hơn “bật thêm flag”.

Triệu chứng Nguyên nhân khả dĩ Kiểm tra Hướng xử lý
TTFT cao Prompt dài, prefill, queue length hist, queue, prefill time prefix cache, chunked prefill, scale, tune scheduler
ITL cao Decode BW, batch nhỏ, KV dài decode time, BW, active seq continuous batching, concurrency hợp lý, quant KV
OOM KV lớn, max_len/seqs cao GPU mem, KV blocks giảm max_len/seqs, FP8 KV, TP
Throughput thấp Batch nhỏ, tokenizer/CPU GPU/CPU util, queue tăng load, tune batched tokens, optimize tokenizer
p99 xấu Length outliers, preemption latency theo length admission control, length buckets, separate pools
Stream giật Chunk/network, decode stall per-token timestamps flush, scheduler, network
Prefix hit thấp mismatch token, eviction hit metrics normalize prompt, template, salt policy
Spec không nhanh acceptance thấp, draft đắt accepted tokens, draft lat giảm draft len, đổi method, off/on

Cost per 1M output tokens (compute GPU, chưa gồm CPU/network/obs):

\[ \text{effective\_tps} = \text{measured\_output\_tps} \times \text{safety\_factor} \]

\[ \text{cost\_per\_1M} = \frac{\text{GPU\_count} \times \text{GPU\_hour\_price}}{\text{effective\_tps} \times 3600} \times 10^{6} \]

Ví dụ: 4 GPU × $3/h, measured 8000 tok/s, safety 0.7 → effective 5600 → ≈ $0.595 / 1M output tokens.

Capacity:

\[ \text{required\_gpus} = \left\lceil \frac{\text{required\_output\_tps}}{\text{safe\_tps\_per\_gpu}} \right\rceil \]

và đồng thời:

\[ \text{max\_concurrent} \le \frac{\text{available\_KV\_memory}}{\text{avg\_KV\_per\_sequence}} \]

Lab 1: KV cache memory calculator

from dataclasses import dataclass

@dataclass
class ModelKVConfig:
    num_layers: int
    num_kv_heads: int
    head_dim: int
    bytes_per_element: int

def kv_cache_bytes(config: ModelKVConfig, sequence_length: int, batch_size: int = 1) -> int:
    return (
        batch_size
        * config.num_layers
        * sequence_length
        * 2
        * config.num_kv_heads
        * config.head_dim
        * config.bytes_per_element
    )

def gib(num_bytes: int) -> float:
    return num_bytes / (1024 ** 3)

if __name__ == "__main__":
    config = ModelKVConfig(
        num_layers=32, num_kv_heads=8, head_dim=128, bytes_per_element=2
    )
    for seq_len in [1024, 2048, 4096, 8192, 32768]:
        per_request = kv_cache_bytes(config, seq_len)
        batch_32 = kv_cache_bytes(config, seq_len, batch_size=32)
        print(
            f"seq_len={seq_len:>6} | "
            f"per_request={gib(per_request):6.2f} GiB | "
            f"batch32={gib(batch_32):7.2f} GiB"
        )
python kv_cache_calculator.py

Bài tập: đổi num_kv_heads 8→32 (MHA vs GQA); bytes_per_element 2→1 (FP8 KV); tính batch tối đa nếu còn 40 GiB cho KV.

Lab 2: Đo TTFT / ITL với streaming client

Giả sử OpenAI-compatible endpoint tại http://localhost:8000/v1:

import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
model = "your-model-name"
messages = [
    {"role": "system", "content": "You are a concise technical tutor."},
    {"role": "user", "content": "Explain KV cache in LLM inference in 5 bullet points."},
]

start = time.perf_counter()
first_token_time = None
last_token_time = None
num_chunks = 0
collected_text = []

stream = client.chat.completions.create(
    model=model,
    messages=messages,
    max_tokens=256,
    temperature=0.2,
    stream=True,
)

for event in stream:
    now = time.perf_counter()
    token_text = (event.choices[0].delta.content or "")
    if token_text:
        if first_token_time is None:
            first_token_time = now
        last_token_time = now
        num_chunks += 1
        collected_text.append(token_text)
        print(token_text, end="", flush=True)

end = time.perf_counter()
print("\n")
if first_token_time is None:
    print("No token received.")
else:
    ttft = first_token_time - start
    e2e = end - start
    generation_time = (last_token_time or end) - first_token_time
    avg_itl = generation_time / max(num_chunks - 1, 1)
    print(f"TTFT: {ttft:.3f} s")
    print(f"E2E latency: {e2e:.3f} s")
    print(f"Chunks received: {num_chunks}")
    print(f"Approx avg ITL per chunk: {avg_itl:.3f} s")

Lưu ý: đo theo chunk text, không phải token tuyệt đối; network/client ảnh hưởng kết quả.

Lab 9 — cost calculator

import math

def cost_per_million_output_tokens(
    gpu_count: int, gpu_hour_price: float,
    measured_output_tps: float, safety_factor: float = 0.7,
) -> float:
    effective_tps = measured_output_tps * safety_factor
    if effective_tps <= 0:
        raise ValueError("effective_tps must be positive")
    return gpu_count * gpu_hour_price / (effective_tps * 3600) * 1_000_000

def required_gpus(
    target_output_tps: float, measured_tps_per_gpu_at_slo: float,
    safety_factor: float = 0.7,
) -> int:
    safe_tps = measured_tps_per_gpu_at_slo * safety_factor
    if safe_tps <= 0:
        raise ValueError("safe_tps must be positive")
    return math.ceil(target_output_tps / safe_tps)

if __name__ == "__main__":
    print("Cost per 1M:", cost_per_million_output_tokens(4, 3.0, 8000, 0.7))
    print("Required GPUs:", required_gpus(50000, 2000, 0.7))

MẹoTự kiểm — đáp án ngắn
  1. Mỗi step ít token mới nhưng đọc KV ngày càng dài → thường bị memory bandwidth, GPU dễ underutilized nếu batch nhỏ.
  2. Key/value attention đã tính; \(\text{bytes}=L\cdot S\cdot 2\cdot H_{kv}\cdot d\cdot b\).
  3. Prefill xử lý cả prompt → tạo KV + first logits; prompt/queue/prefill nặng → TTFT tăng.
  4. ITL phản ánh khoảng cách giữa token decode; decode chậm/stall → ITL xấu.
  5. Static giữ batch cố định tới khi mọi request xong; continuous đổi tập sequence mỗi iteration.
  6. Virtual memory / paging: logical block → physical block không cần contiguous.
  7. Nhiều request cùng prefix token-level (system prompt, template, RAG) và cache chưa evict.
  8. Request khác nhau về input/output tokens; cùng RPS có thể khác xa công việc GPU.
  9. Acceptance cao, draft rẻ, target lớn/decode memory-bound, QPS chưa saturate, output đủ dài.
  10. Cần ceiling trên NVIDIA, team tune được, quant/multi-GPU path tối ưu, workload đủ lớn justify effort.
  11. Tăng max_model_len tăng KV reserve/demand → ít concurrent sequences hơn, cost/capacity đổi.
  12. Đo output TPS tại mức vẫn đạt SLO × safety factor; chia chi phí GPU-giờ cho effective TPS rồi scale về 1M tokens.
  13. Giảm num_kv_heads so với số query heads → hệ số \(H_{kv}\) trong công thức nhỏ hơn.
  14. Chia prefill dài thành chunk, xen decode → giữ ITL mượt hơn khi có prompt dài.
  15. Goodput chỉ đếm request/tokens thỏa SLO; raw TPS có thể cao nhưng nhiều request “hỏng UX”.
  16. Budget nhỏ hơn thường giúp ITL; lớn hơn thường giúp TTFT/prefill throughput — cần bench workload thật.
  17. Throughput constraint, KV memory constraint, latency SLO (TTFT/ITL) constraint.
  18. Nhiều adapter/task/tenant trên cùng base model — tăng mật độ serve, vẫn phải quản lý memory/isolation.
  19. Nhiều SSE/chunk, detokenize lặp, giữ HTTP lâu, backpressure, logging/tracing nhiều event.
  20. Queue time, prompt length, prefix hit, trộn long/short traffic, GPU saturation, tokenizer CPU.

Summary

  • LLM serving = prefill + decode loop + streaming; metric đúng là TTFT / ITL / tokens/s / goodput, không chỉ RPS.
  • KV cache là tài nguyên nóng: ước lượng bằng \(L\cdot S\cdot 2\cdot H_{kv}\cdot d\cdot b\); MQA/GQA và quant KV tăng capacity.
  • Continuous / in-flight batching thay static batch khi output length lệch; chunked prefill giữ decode mượt khi prompt dài.
  • PagedAttention + prefix caching giảm waste/fragmentation và TTFT trên traffic lặp prefix.
  • Speculative decoding và TP/PP/EP là tối ưu có điều kiện — đo acceptance, communication và p99.
  • vLLM = velocity + HF/API; TensorRT-LLM = NVIDIA ceiling; quant LLM (FP8/INT4/AWQ…) đổi memory/throughput lấy risk quality.
  • Production: streaming có overhead; dashboard token-level; debug theo bảng triệu chứng; cost theo tokens dưới SLO; checklist trước launch.
Serve tokens under SLO — not just maximize GPU utilization.
