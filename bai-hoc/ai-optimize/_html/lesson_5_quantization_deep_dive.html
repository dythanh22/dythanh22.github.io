5.1 Vì sao quantization quan trọng?

Tại sao giảm precision của số có thể giúp inference nhanh hơn, và khi nào nó không giúp?

Quan trọngÝ chính

Quantization giảm số byte mỗi weight/activation, từ đó giảm memory bandwidth và kích hoạt low-precision kernel trên hardware hỗ trợ. Tuy nhiên, không tự động nhanh hơn — chỉ nhanh hơn khi runtime, compiler và hardware thật sự sử dụng được low-precision kernels hiệu quả.

Model inference thường bị giới hạn bởi một hoặc nhiều bottleneck:

Bottleneck Mô tả
Compute throughput TFLOPS bị bão hòa
Memory bandwidth Di chuyển weights/activations quá chậm
GPU memory capacity Model không vừa VRAM
CPU / kernel overhead Launch overhead dominate, model quá nhỏ

Quantization chủ yếu giúp ở memory bandwidth và compute throughput khi có low-precision kernel:

Type Bytes/value Ghi chú
FP32 4 Baseline high precision
FP16 / BF16 2 Mixed precision phổ biến trên GPU
INT8 / FP8 1 Thường dùng để tăng tốc inference
INT4 / FP4 0.5 Weight-only hoặc model rất lớn 
Nếu model bị memory bandwidth bound:
    quantization có thể giúp rất nhiều.
Nếu model bị overhead bound hoặc layer không có low-precision kernel:
    quantization có thể không giúp, thậm chí chậm hơn.
MẹoĐào sâu: Quantization không phải pruning / distillation / compilation

Bốn kỹ thuật này đều giảm cost inference nhưng hoạt động hoàn toàn khác:

Kỹ thuật Cơ chế Thay đổi structure? Thay đổi precision?
Pruning Xóa weight / neuron / head / channel Có Không
Distillation Train model nhỏ theo model lớn Có (model khác) Không
Compilation Tối ưu schedule, fusion, layout Không Không
Quantization Giảm numeric precision Không Có

Production thường kết hợp cả bốn nhóm:

training → distillation / pruning
export → ONNX
optimization → quantization + compilation
serving → batching + scheduling + monitoring

5.2 Nền tảng số học

Scale, zero-point và affine formula nghĩa là gì trong thực tế?

Quan trọngÝ chính

Quantization ánh xạ FP32 sang integer bằng công thức affine: q = round(x / scale + zero_point), rồi dequantize về x_approx = scale × (q − zero_point). Scale và zero-point xác định toàn bộ độ chính xác và range biểu diễn.

Công thức affine chuẩn:

\[q = \operatorname{round}\!\left(\frac{x}{\text{scale}} + \text{zero\_point}\right)\]

\[x_{\text{approx}} = \text{scale} \times (q - \text{zero\_point})\]

Ký hiệu Ý nghĩa
x Giá trị gốc FP32 / FP16
q Giá trị đã quantize INT8 / UINT8
scale Hệ số ánh xạ real value → integer range
zero_point Integer đại diện cho giá trị 0.0
round Làm tròn sang mức biểu diễn gần nhất
clip / clamp Cắt giá trị vượt representable range

Range biểu diễn:

  • INT8 signed: q ∈ [−128, 127] — 256 mức
  • UINT8: q ∈ [0, 255] — 256 mức

Với symmetric INT8 (zero_point = 0):

\[q = \operatorname{clamp}\!\left(\operatorname{round}\!\left(\frac{x}{\text{scale}}\right),\; -128,\; 127\right)\]

\[x_{\text{approx}} = q \times \text{scale}\]

MẹoĐào sâu: Tại sao zero_point quan trọng?

zero_point đảm bảo giá trị 0.0 trong FP32 được biểu diễn chính xác bằng một giá trị integer. Điều này quan trọng vì:

  • Padding tensor dùng 0 — sai zero là sai toàn bộ padding
  • ReLU output bắt đầu từ 0 — nếu 0 bị biểu diễn sai, sai số lan qua toàn mạng
  • Activation sau ReLU (luôn ≥ 0): UINT8 có thể biểu diễn hiệu quả hơn INT8 signed

Với asymmetric UINT8: zero_point ∈ [0, 255], zero-point “dịch” toàn bộ range để căn với phân phối lệch của activation.

5.3 Symmetric vs asymmetric quantization

Nên dùng symmetric hay asymmetric cho weights và activations?

Quan trọngÝ chính

Symmetric (zero_point = 0) đơn giản hơn, tốt cho hardware acceleration và phù hợp với weights vì phân phối weights thường đối xứng quanh 0. Asymmetric dùng zero-point để căn phân phối lệch, tốt hơn cho activations sau ReLU. TensorRT hiện đại thường dùng symmetric INT8 cho weights qua Q/DQ workflow.

Đặc điểm Symmetric Asymmetric
zero_point 0 (hoặc gần 0) Giá trị bất kỳ trong range
Công thức q = round(x / scale) q = round(x / scale + zp)
Ưu điểm Đơn giản, hardware tốt Tốt hơn cho phân phối lệch
Nhược điểm Có thể lãng phí range nếu lệch Phức tạp hơn, support kém hơn
Dùng cho Weights (phân phối đối xứng) Activations (thường lệch)

Quy tắc thực tế:

Weights:      symmetric + per-channel (phân phối thường đối xứng quanh 0)
Activations:  per-tensor; symmetric hoặc asymmetric tùy backend
TensorRT:     ưu tiên explicit Q/DQ graph với scale rõ ràng
Cảnh báoBẫy thường gặp

Một số backend/hardware hỗ trợ kém asymmetric quantization cho activations — có thể fallback FP32 hoặc không có kernel tốt. Luôn kiểm tra layer profile sau khi build engine.

5.4 Rounding error và clamping error

Quantization gây lỗi ở đâu và hai loại lỗi trade-off với nhau thế nào?

Quan trọngÝ chính

Có hai nguồn lỗi chính: rounding error (mức biểu diễn quá thô) và clamping error (giá trị vượt range bị cắt mất). Scale lớn giảm clamping nhưng tăng rounding; scale nhỏ giảm rounding nhưng tăng clamping. Calibration là quá trình chọn scale cân bằng tối ưu hai loại lỗi này dựa trên distribution thực tế.

Rounding error xảy ra khi nhiều giá trị thực khác nhau bị map vào cùng một integer:

scale = 0.1
x = 1.04  →  q = round(10.4) = 10  →  x_approx = 1.0   (lỗi: 0.04)
x = 1.06  →  q = round(10.6) = 11  →  x_approx = 1.1   (lỗi: 0.04)

Scale lớn → mỗi step rộng → rounding error lớn hơn.

Clamping error xảy ra khi giá trị vượt range biểu diễn INT8:

q = clamp(round(x / scale), -128, 127)
Nếu x / scale > 127: q bị kẹt ở 127 → thông tin bị mất hoàn toàn

Scale nhỏ → representable range hẹp → dễ clamp outliers.

Scale Rounding error Clamping error
Lớn Cao Thấp
Nhỏ Thấp Cao
Optimal (calibration) Cân bằng Cân bằng
MẹoVí dụ trực giác: vector FP32 → INT8 có và không có outlier 20.0

Không có outlier:

x = [-1.0, -0.5, 0.0, 0.5, 1.0]
scale = max(abs(x)) / 127 = 1.0 / 127 ≈ 0.00787

q     = [-127, -64, 0, 64, 127]
x_hat ≈ [-1.0, -0.504, 0.0, 0.504, 1.0]
MAE nhỏ — biểu diễn tốt cho toàn bộ vector.

Có outlier 20.0:

x = [-1.0, -0.5, 0.0, 0.5, 20.0]
scale = 20.0 / 127 ≈ 0.1575

0.5 / scale ≈ 3.175  →  q = 3  →  x_approx ≈ 0.472
(giá trị nhỏ bị biểu diễn thô hơn rất nhiều — mất 5.6% giá trị gốc)

Outlier 20.0 kéo scale lên 20×, làm toàn bộ phân phối chính bị rounding thô. Đây là lý do Entropy/Percentile calibration hữu ích: loại bỏ ảnh hưởng của outliers hiếm để tối ưu cho phần lớn distribution.

5.5 Granularity

Per-tensor, per-channel, per-block khác nhau thế nào và khi nào dùng?

Quan trọngÝ chính

Granularity xác định có bao nhiêu scale/zero-point được dùng cho một tensor. Per-channel cho weights thường tốt hơn per-tensor về accuracy vì từng channel có range khác nhau. Per-tensor cho activations phổ biến vì đơn giản và kernel dễ hỗ trợ.

Granularity Scale shape Ưu điểm Nhược điểm
Per-tensor [] (scalar) Đơn giản, runtime overhead thấp Kém nếu channels có range rất khác nhau
Per-channel [out_channels] Accuracy tốt cho weights, giảm ảnh hưởng outlier channel Scale nhiều hơn; kernel cần support per-channel
Per-block [M, ceil(K/bs)] Cân bằng accuracy/overhead cho LLM Phức tạp; backend support khác nhau

Quy tắc thực tế:

CNN Conv weights:      per-channel (axis = out_channel)
Activations:           per-tensor
LLM / large GEMM:     per-channel hoặc per-block weight-only
TensorRT khởi đầu:     per-tensor activation + per-channel weight
MẹoĐào sâu: Weight quantization vs activation quantization

Weight quantization dễ hơn — weights là constants sau training: - Scan toàn bộ weight tensor offline, tính scale chính xác một lần - Dùng per-channel / per-block dễ - Ổn định: không phụ thuộc vào input distribution

Activation quantization phụ thuộc input: - Distribution = function(input data) → cần calibration dataset đại diện - Phải dùng static scale (offline calibration) hoặc dynamic scale (runtime) - Nhạy với distribution shift giữa calibration và production - Là nguyên nhân lớn nhất gây accuracy drop trong PTQ

Kết hợp phổ biến nhất: weight quantization per-channel + activation quantization per-tensor.

5.6 Dynamic quantization vs static quantization

Tính scale lúc inference hay offline — cái nào phù hợp khi nào?

Quan trọngÝ chính

Dynamic quantization tính scale activation tại runtime — không cần calibration data nhưng có overhead. Static quantization tính scale offline từ calibration dataset — inference nhanh hơn nhưng đòi hỏi data đại diện. CNN serving trên GPU nên ưu tiên static + Q/DQ; CPU NLP workload có thể thử dynamic.

Tiêu chí Dynamic Static
Scale activation Runtime, mỗi input Offline, cố định sau calibration
Calibration data cần Không (activation) Có
Inference overhead Cao hơn Thấp hơn
Accuracy Thường tốt hơn theo từng input Phụ thuộc chất lượng calibration
Phù hợp RNN / Transformer CPU CNN / GPU serving
Model / Workload Gợi ý ban đầu
CNN image classification / detection Static PTQ trước
RNN / một số NLP CPU Dynamic PTQ có thể thử
Transformer / LLM GPU Framework-specific PTQ / QAT / weight-only / FP8
Accuracy target rất chặt QAT hoặc mixed precision
Không có calibration data Dynamic hoặc weight-only quantization

5.7 PTQ: Post-Training Quantization

Quantize sau khi model đã train xong hoạt động thế nào và cần gì?

Quan trọngÝ chính

PTQ không retrain model — chỉ thu thập thống kê activation từ calibration data, tính scale/zero-point, rồi tạo quantized graph. Nhanh và không cần training data đầy đủ, nhưng accuracy phụ thuộc hoàn toàn vào chất lượng calibration data và phương pháp calibration.

Khi nào dùng PTQ:

  • Deploy nhanh, không có budget retraining
  • Không có full training data
  • Model có kiến trúc quantization-friendly (CNN vision phổ biến)
  • Accuracy drop chấp nhận được trong ngưỡng business

PTQ workflow tiêu chuẩn (10 bước):

  1. Chọn baseline model FP32/FP16 → đo accuracy + latency
  2. Chuẩn bị calibration dataset (xem yêu cầu bên dưới)
  3. Chạy graph preprocessing/fusion nếu framework yêu cầu
  4. Chạy calibration → tính scale/zero-point
  5. Tạo quantized model (Q/DQ ONNX hoặc QOperator)
  6. Validate accuracy trên validation set thật
  7. Benchmark latency/throughput/memory
  8. Debug layer gây lỗi (xem Mục 5.12)
  9. Exclude sensitive layers hoặc thử calibration method khác
  10. Nếu vẫn không đạt → chuyển sang QAT hoặc mixed precision

Calibration dataset — yêu cầu:

Calibration data không cần label, nhưng phải đại diện cho distribution inference và phải đi qua đúng preprocessing pipeline production:

Tốt:
    ảnh production thật, đủ class, đủ lighting / scale / source
    preprocessing: resize → center crop → normalize(mean/std) → NCHW
    đúng như production inference

Không tốt:
    ảnh random noise                input shape khác production
    chỉ một class                   normalize khác production
    sample quá ít                   augmented data quá khác inference

Ba calibration methods:

Method Cơ chế Ưu điểm Nhược điểm
MinMax range = [min_act, max_act] Đơn giản, nhanh, giữ toàn range Rất nhạy với outlier
Entropy / KL Chọn threshold tối ưu hóa KL divergence Tốt cho CNN, giảm ảnh hưởng outlier Chậm hơn; tệ nếu outlier thật sự quan trọng
Percentile threshold = percentile(abs(act), p) Dễ hiểu, cân bằng min-max và entropy p là hyperparameter; quá thấp → clamping lớn 
Bắt đầu: MinMax hoặc Entropy tùy backend / model
Nếu accuracy drops: thử method khác → per-channel weights
  → exclude sensitive layers → kiểm tra preprocessing
  → tăng calibration data → chuyển sang QAT nếu cần

5.8 QAT: Quantization-Aware Training

Khi nào PTQ không đủ tốt và cần training lại với fake quantization?

Quan trọngÝ chính

QAT chèn fake quantization vào training graph: forward pass mô phỏng quantization noise, backward pass dùng Straight-Through Estimator. Model học cách robust với rounding/clamping, phục hồi accuracy gần FP32 mà PTQ không thể đạt. Cần training compute budget và full training/fine-tuning data.

Fake quantization là gì:

Forward pass:
    x_fp32 → quantize → dequantize → x_fake_quant_fp32
    (model thấy lỗi quantization, học để minimize nó)

Backward pass:
    Gradient đi qua Straight-Through Estimator (STE)
    Optimizer cập nhật weights để giảm quantization error

Vì sao QAT giúp accuracy:

PTQ chỉ thay đổi representation sau training — model không có cơ hội thích nghi với rounding/clamping. QAT cho model fine-tune với quantization noise nên có thể:

  • Giảm sensitivity của weights với quantization
  • Điều chỉnh activation distribution về range dễ quantize hơn
  • Giảm lỗi tại layer nhạy cảm
  • Khôi phục accuracy gần FP32 hơn nhiều so với PTQ

Khi nào cần QAT:

  • PTQ accuracy drop vượt ngưỡng chấp nhận
  • Model nhỏ, capacity thấp (ít parameter chịu được quantization hơn)
  • Activation distribution khó calibrate (irregular, long-tail)
  • Object detection / segmentation bị giảm mAP nhiều
  • Accuracy target rất chặt (medical, finance)
  • Có training / fine-tuning data và compute budget

QAT workflow tiêu chuẩn:

  1. Start từ pretrained FP32/FP16 model
  2. Fuse modules nếu framework yêu cầu (BatchNorm + Conv)
  3. Insert observers / fake quant modules
  4. Fine-tune vài epoch với learning rate nhỏ
  5. Freeze observer sau khi scale ổn định
  6. Freeze batch norm statistics nếu cần
  7. Convert / export sang quantized graph hoặc ONNX Q/DQ graph
  8. Validate accuracy → build TensorRT engine → benchmark thật
Cảnh báoBẫy thường gặp với QAT

QAT vẫn fail nếu pipeline sai:

  • Fake quant config không khớp backend thật (per-channel axis sai, dtype khác)
  • Preprocessing training ≠ production
  • Export ONNX không giữ đúng Q/DQ nodes
  • Observer chưa ổn định (scale còn dao động khi convert)
  • Layer sensitive bị ép quantize trong khi backend không fuse tốt
  • Không validate engine thật — chỉ đo accuracy trong PyTorch

Bắt buộc: export ONNX Q/DQ sớm trong QAT và validate TensorRT/ORT engine ngay trong quá trình fine-tuning.

MẹoPyTorch QAT skeleton (conceptual) 
import torch
from torch.ao.quantization import get_default_qat_qconfig_mapping
from torch.ao.quantization.quantize_fx import prepare_qat_fx, convert_fx


model = MyModel()
model.train()

example_inputs = (torch.randn(1, 3, 224, 224),)
qconfig_mapping = get_default_qat_qconfig_mapping("fbgemm")

prepared = prepare_qat_fx(model, qconfig_mapping, example_inputs)

for epoch in range(num_epochs):
    prepared.train()
    for images, labels in train_loader:
        optimizer.zero_grad()
        outputs = prepared(images)
        loss = criterion(outputs, labels)
        loss.backward()
        optimizer.step()
    validate(prepared, val_loader)

prepared.eval()
quantized = convert_fx(prepared)

Lưu ý quan trọng: PyTorch quantized model ≠ TensorRT-ready. Phải kiểm tra export ONNX Q/DQ, TensorRT parsing và accuracy sau khi build engine thật.

5.9 ONNX quantization representation

ONNX biểu diễn quantization bằng cách nào và tại sao Q/DQ tốt hơn QOperator?

Quan trọngÝ chính

ONNX có hai format: QOperator (thay op gốc bằng quantized op chuyên biệt như QLinearConv) và Q/DQ (chèn QuantizeLinear/DequantizeLinear quanh tensor, giữ op gốc). TensorRT hiện đại ưu tiên Q/DQ vì cho phép compiler kiểm soát precision boundary rõ ràng và fuse pattern hiệu quả.

QOperator format:

Conv    → QLinearConv
MatMul  → MatMulInteger / QLinearMatMul

Graph nhìn ngắn hơn, phù hợp một số CPU backend. Nhưng phụ thuộc hoàn toàn vào support từng quantized op type.

Q/DQ format giữ operator gốc, chèn precision boundary:

x_fp32
  ↓  QuantizeLinear(scale, zero_point)
x_int8
  ↓  DequantizeLinear(scale, zero_point)
x_fp32_approx
  ↓  Conv (FP32 op gốc)
  ↓  QuantizeLinear → y_int8 → DequantizeLinear → y_fp32_approx

Backend (TensorRT / ORT) nhận ra pattern DQ → Conv → Q và fuse thành INT8 Conv kernel.

ONNX operators:

QuantizeLinear (opset 13+):

\[y = \operatorname{saturate}\!\left(\operatorname{round}\!\left(\frac{x}{y\_\text{scale}}\right) + y\_\text{zero\_point}\right)\]

DequantizeLinear:

\[y = (x - x\_\text{zero\_point}) \times x\_\text{scale}\]

Tại sao Q/DQ rồi dequantize ngay?

Graph vẫn biểu diễn toán học ở dạng FP32 approximation, nhưng backend nhận ra pattern và thay bằng low-precision kernel. Lợi ích: compiler tự quyết định fuse hay không theo hardware capability; precision boundary rõ ràng dễ debug.

Tiêu chí QOperator Q/DQ
Graph ngắn gọn Có Ít hơn
Precision control Thấp Cao
TensorRT fusion Giới hạn Tốt
CPU backend support Tốt Tùy provider
Kiểm soát sensitive layer Khó Dễ
Hướng phát triển TRT Legacy Ưu tiên
MẹoQ/DQ placement recommendations

Quantize inputs của weighted ops:

Conv, GEMM, MatMul, FullyConnected, Transposed Conv
→ Q/DQ trước activation input + weight input của các op này

Cấu hình khởi đầu đáng thử:

weights:     per-channel / per-axis
activations: per-tensor

Cẩn thận với activation nhạy cảm:

SiLU / Swish     Softmax        LayerNorm
GELU             Attention score matmul
Small residual add values

Không phải lúc nào cũng nên ép mọi thứ chạy INT8/FP8.

Residual connections cần chú ý:

main branch → Conv → Add → output
skip branch ─────────^

Nếu một nhánh quantized và nhánh kia FP16, compiler có thể không fuse tốt. Kiểm tra precision của cả hai input vào Add và output của Add.

Không thêm Q/DQ quá aggressive:

Thêm quá nhiều Q/DQ → graph nhiều conversion → chặn fusion → accuracy drop → build fail nếu không có low-precision kernel.

Quantize where it pays off.
Keep sensitive regions higher precision.

5.10 Explicit vs implicit quantization trong TensorRT

TRT explicit quantization với Q/DQ khác gì implicit calibration?

Quan trọngÝ chính

Explicit quantization encode scale/zero_point trong graph bằng Q/DQ nodes — TensorRT đọc và fuse chúng, kiểm soát precision rõ ràng, hỗ trợ nhiều dtype. Implicit quantization để TRT tự quyết dựa trên external calibration table. Pipeline mới phải dùng explicit Q/DQ; không đưa external calibration table vào model đã có Q/DQ nodes.

Đặc điểm Implicit quantization Explicit quantization
Scale nằm ở đâu Calibration table ngoài Q/DQ nodes trong graph
Kiểm soát precision Thấp Cao
Dtype support Chỉ INT8 INT8, FP8, INT4, …
Strong typing Không Có (stronglyTyped mode)
Hướng phát triển Legacy Ưu tiên workflow mới

Quy tắc quan trọng nhất:

Model đã có Q/DQ nodes:
    → KHÔNG đưa external INT8 calibration table vào TensorRT.
    Lý do: scale đã encode trong graph; calibration table ngoài
    sẽ xung đột và gây lỗi hoặc override không mong muốn.

Model chưa có Q/DQ nodes:
    → Cần calibration / dynamic range cho implicit INT8.
    Hoặc: dùng quantization tool tạo Q/DQ graph trước.

TRT xử lý Q/DQ graph:

Khi TensorRT thấy Q/DQ nodes, compiler cố gắng:

  1. Propagate Q backward (đẩy quantization sớm hơn trong graph)
  2. Propagate DQ forward (đẩy dequantization muộn hơn)
  3. Fuse DQ + quantizable_op + Q thành INT8/FP8 kernel
  4. Tăng phần graph chạy low precision
  5. Giữ arithmetic correctness trong phạm vi optimization hợp lệ
Q/DQ nodes are precision boundaries.
Compiler moves and fuses them safely.

Q/DQ placement ảnh hưởng trực tiếp đến:

  • Layer nào chạy INT8/FP8 thật sự
  • Có fuse được hay không
  • Có fallback về FP16/FP32 hay không
  • Accuracy có giảm mạnh hay không

5.11 INT8 trong TensorRT và FP8

INT8 trong TensorRT hoạt động thế nào và FP8 khi nào nên dùng?

Quan trọngÝ chính

INT8 trong TensorRT dùng symmetric quantization với roundWithTiesToEven. Nhanh hơn không chỉ vì size nhỏ hơn — phải có low-precision kernel được fuse và chạy thật. trtexec --int8 không có Q/DQ hoặc calibration đúng chỉ benchmark tốc độ, không phải accuracy validation. FP8 cần hardware mới hơn và không phải drop-in replacement cho INT8.

INT8 symmetric quantization formula trong TensorRT:

\[x_q = \operatorname{roundWithTiesToEven}\!\left(\operatorname{clip}\!\left(\frac{x}{\text{scale}},\; -128,\; 127\right)\right)\]

\[x = x_q \times \text{scale}\]

Trong đó scale là FP16/FP32/BF16 per-tensor hoặc per-channel.

INT8 giúp khi TensorRT có thể fuse low-precision kernel:

DQ → Conv → Q       →  INT8 Conv (Tensor Core)
DQ → MatMul → Q     →  INT8 GEMM kernel

Nhưng nếu graph bị nhiều conversion xen kẽ:

INT8 → FP32 → INT8 → FP32

overhead có thể ăn hết lợi ích của low precision.

Implicit INT8 calibration flow trong TensorRT (legacy / không-Q/DQ):

1. Build FP32 engine tạm
2. Run calibration dataset qua engine
3. Ghi histogram/statistics cho activation tensors
4. Tạo calibration table chứa scale values
5. Build INT8 engine dùng calibration table

Calibration cache để tránh chạy lại mỗi lần build. Workflow mới nên dùng Q/DQ ONNX → TensorRT explicit quantization.

FP8 vs INT8:

Tiêu chí INT8 FP8 (E4M3)
Type Integer Floating point
Bit format 8-bit uniform 1 sign + 4 exp + 3 mantissa
Value spacing Uniform theo scale Non-uniform (nhiều giá trị gần zero)
Cần scale Có Có (trong TRT Q/DQ workflow)
Hardware support GPU đời rộng hơn Thường cần Hopper+ (H100)
Use case phổ biến CNN / GEMM / activation Transformer / LLM / diffusion hiện đại

Khi nào nên quan tâm FP8:

  • GPU hỗ trợ FP8 tốt (Hopper+)
  • Đang làm Transformer / LLM / VLM / diffusion inference
  • Dùng TensorRT hoặc TensorRT-LLM / Model Optimizer workflow
  • Cần throughput cao với accuracy tốt hơn một số INT8 path

Thứ tự học đúng:

1. FP32 baseline
2. FP16 baseline
3. INT8 PTQ / QAT
4. Q/DQ graph debugging
5. FP8

Đừng học FP8 trước khi hiểu scale, calibration, Q/DQ và accuracy recovery.

5.12 Accuracy recovery

Khi quantized model bị accuracy drop, debug và phục hồi thế nào?

Quan trọngÝ chính

Đừng đoán — debug có hệ thống theo 8 bước: xác nhận baseline → kiểm tra preprocessing → cải thiện calibration data → thử calibration method khác → so sánh activation tensors → exclude sensitive layers → mixed precision → QAT. Hầu hết production accuracy drop đến từ preprocessing sai hoặc calibration data không đại diện.

Bước 1 — Xác nhận baseline:

[ ] FP32/FP16 model accuracy được ghi lại
[ ] FP32/FP16 baseline latency được ghi lại
[ ] preprocessing version, dataset version, input shape, opset, runtime, hardware

Nếu baseline không ổn định, mọi so sánh sau vô nghĩa.

Bước 2 — Kiểm tra preprocessing:

[ ] resize giống production          [ ] RGB/BGR đúng
[ ] crop giống production            [ ] normalize mean/std đúng
[ ] NCHW/NHWC đúng                   [ ] dtype đúng (float32)
[ ] batch dimension đúng             [ ] dynamic shape đúng
[ ] calibration dùng cùng preprocessing với production

Rất nhiều lỗi INT8 đến từ preprocessing sai — kiểm tra đây trước.

Bước 3 — Cải thiện calibration data:

[ ] Đủ đa dạng (không chỉ vài batch đầu)
[ ] Có edge cases của production
[ ] Không dùng augmented data quá khác inference
[ ] Không dùng random / noise data
[ ] Batch order randomized
[ ] Số sample đủ cho activation statistics

Không có con số universal. Với CNN classification: ablation theo số sample:

50 → 100 → 250 → 500 → 1000 → 2000
vẽ curve: calibration_size vs validation_accuracy

Bước 4 — Thử calibration method khác:

MinMax fail?  →  thử Entropy / KL
Entropy fail? →  thử MinMax cho transformer/NLP-like layers
              →  thử exclude attention / softmax / layer norm
Thêm:         →  per-channel weights
              →  reduce_range nếu CPU backend cần

Bước 5 — So sánh activation tensors:

Tìm layer đầu tiên nơi error bùng lên:

FP32 model intermediate outputs
vs
Quantized model intermediate outputs

Metric: MAE, max abs error, cosine similarity, KL divergence, relative error

for each matched activation:
    error[layer] = compare(fp32_activation, int8_activation)
sort layers by error descending
inspect first large divergence

Bước 6 — Exclude sensitive layers:

Candidate layers nên giữ FP16 / FP32:
  first conv / stem         softmax
  last classifier           layer norm
  attention score matmul    small residual add
  custom op                 SiLU / GELU nhạy

Quy tắc: start aggressive → dequantize sensitive layers dần
         cho đến khi accuracy phục hồi.

Bước 7 — Mixed precision:

some layers → INT8 / FP8
some layers → FP16
some layers → FP32

Thực tế production:
  80% compute-heavy layers → low precision
  20% sensitive layers → high precision

Bước 8 — QAT:

PTQ + calibration tuning + layer exclusion vẫn không đạt:
    → QAT với fake quantization
    → Kèm theo: validation metric sát production,
      same quant config với backend,
      export ONNX Q/DQ sớm và test,
      benchmark TRT/ORT thật — không chỉ đo PyTorch

Failure mode: ONNX Runtime quantized không nhanh

Nguyên nhân: CPU ISA không hỗ trợ, quantized op không được support, QDQ format không phù hợp provider, graph optimization chưa chạy.

Failure mode: FP8 không build hoặc không nhanh

Nguyên nhân: GPU không hỗ trợ FP8, TRT version không phù hợp, ONNX FP8 opset/domain không được toolchain hỗ trợ.

Không hẳn. Backend như TensorRT có thể fuse Q/DQ pattern thành low-precision kernel — overhead gần bằng 0.

Lab 1: Manual quantization bằng NumPy

Mục tiêu: hiểu scale, rounding/clamping error trực tiếp qua code, thấy ảnh hưởng của outlier.

import numpy as np


def symmetric_int8_quantize(x: np.ndarray):
    max_abs = np.max(np.abs(x))
    if max_abs == 0:
        scale = np.float32(1.0)
    else:
        scale = np.float32(max_abs / 127.0)

    q = np.round(x / scale)
    q = np.clip(q, -128, 127).astype(np.int8)
    x_hat = q.astype(np.float32) * scale
    return q, x_hat, scale


def report(name: str, x: np.ndarray):
    q, x_hat, scale = symmetric_int8_quantize(x)
    mae = np.mean(np.abs(x - x_hat))
    max_err = np.max(np.abs(x - x_hat))

    print(f"\n{name}")
    print("x       =", x)
    print("scale   =", scale)
    print("q       =", q)
    print("x_hat   =", x_hat)
    print("mae     =", mae)
    print("max_err =", max_err)


x1 = np.array([-1.0, -0.5, 0.0, 0.5, 1.0], dtype=np.float32)
x2 = np.array([-1.0, -0.5, 0.0, 0.5, 20.0], dtype=np.float32)

report("without outlier", x1)
report("with outlier   ", x2)

  3. Nếu dùng percentile(abs(x), 99) thay vì max, outlier 20.0 ảnh hưởng thế nào?

import numpy as np
import onnx
from onnxruntime.quantization import (
    CalibrationDataReader,
    QuantFormat,
    QuantType,
    CalibrationMethod,
    quantize_static,
)


class NumpyCalibrationDataReader(CalibrationDataReader):
    def __init__(self, input_name: str, samples: list):
        self.input_name = input_name
        self.samples = samples
        self.index = 0

    def get_next(self):
        if self.index >= len(self.samples):
            return None
        sample = self.samples[self.index]
        self.index += 1
        return {self.input_name: sample}


fp32_model = "model.onnx"
qdq_model = "model.static.qdq.int8.onnx"

model = onnx.load(fp32_model)
input_name = model.graph.input[0].name

# Lab dùng random data để minh họa API.

samples = [
    np.random.randn(1, 3, 224, 224).astype(np.float32)
    for _ in range(32)
]
reader = NumpyCalibrationDataReader(input_name, samples)

quantize_static(
    model_input=fp32_model,

Lab 5: Benchmark FP32 vs INT8 bằng ONNX Runtime

Mục tiêu: benchmark có warmup và repeat, so sánh latency, tránh kết luận từ một lần chạy.

import time
import numpy as np
import onnxruntime as ort


def benchmark(model_path: str, x: np.ndarray,
              providers: list, warmup: int = 20, repeat: int = 100):
    sess = ort.InferenceSession(model_path, providers=providers)
    input_name = sess.get_inputs()[0].name

    for _ in range(warmup):
        sess.run(None, {input_name: x})

    times = []
    for _ in range(repeat):
        t0 = time.perf_counter()
        sess.run(None, {input_name: x})
        t1 = time.perf_counter()
        times.append((t1 - t0) * 1000)

    arr = np.array(times)
    return {
        "p50_ms": float(np.percentile(arr, 50)),
        "p90_ms": float(np.percentile(arr, 90)),
        "p99_ms": float(np.percentile(arr, 99)),
        "mean_ms": float(np.mean(arr)),
    }


x = np.random.randn(1, 3, 224, 224).astype(np.float32)
providers = ["CPUExecutionProvider"]

for model in ["model.onnx",
              "model.dynamic.int8.onnx",
              "model.static.qdq.int8.onnx"]:
    print(f"\n{model}")
    print(benchmark(model, x, providers))

Lab 7: Accuracy validation cho quantized model

Mục tiêu: validate accuracy thật trên dataset — không chỉ benchmark latency.

import numpy as np
import onnxruntime as ort


def evaluate_ort(model_path: str, dataloader,
                 providers=None) -> float:
    """
    dataloader: iterable of (images: np.ndarray, labels: np.ndarray)
    Trả về top-1 accuracy.
    """
    if providers is None:
        providers = ["CPUExecutionProvider"]

    sess = ort.InferenceSession(model_path, providers=providers)
    input_name = sess.get_inputs()[0].name

    correct = 0
    total = 0
    for images, labels in dataloader:
        outputs = sess.run(None, {input_name: images})
        preds = np.argmax(outputs[0], axis=1)
        correct += int((preds == labels).sum())
        total += len(labels)

    return correct / total if total > 0 else 0.0

Checkpoint questions

MẹoTự kiểm tra — 20 câu hỏi và đáp án ngắn

  1. Vì sao INT8 có thể nhanh hơn FP32?
    Ít bytes → giảm memory bandwidth; low-precision Tensor Core kernel nhanh hơn với throughput cao hơn.

  2. Vì sao INT8 có thể chậm hơn FP16?
    Hardware không có INT8 acceleration tốt, model nhỏ overhead dominate, Q/DQ quá nhiều, fallback FP32.

  3. Scale và zero-point dùng để làm gì?
    scale ánh xạ real value sang integer range; zero_point xác định integer đại diện 0.0.

  4. Symmetric khác asymmetric ở đâu?
    Symmetric: zero_point = 0; asymmetric: zero_point bất kỳ để căn phân phối lệch.

  5. Vì sao zero phải biểu diễn chính xác trong CNN?
    Padding, ReLU output bắt đầu từ 0; sai zero → sai số lan truyền toàn mạng.

  6. Rounding và clamping trade-off thế nào?
    Scale lớn: ít clamping, nhiều rounding. Scale nhỏ: ít rounding, nhiều clamping. Calibration tìm điểm cân bằng.

  7. Calibration dataset cần label không?
    Không cần label — chỉ cần đại diện distribution và đúng preprocessing.

  8. Calibration dataset cần đại diện production data không?
    Có — nếu không đại diện, scale sẽ sai và accuracy sẽ drop.

  9. Dynamic vs static quantization khác nhau thế nào?
    Dynamic: scale activation tính lúc runtime. Static: scale tính offline từ calibration data.

  10. Vì sao PTQ thường dễ hơn QAT?
    PTQ không cần retrain — chỉ cần calibration data và build graph. Không cần training pipeline.

  11. Vì sao QAT thường chính xác hơn PTQ?
    Model fine-tune với fake quantization noise, học cách robust với rounding/clamping.

  12. ONNX QOperator khác Q/DQ thế nào?
    QOperator thay op gốc bằng quantized op type chuyên biệt. Q/DQ giữ op gốc, chèn precision boundary.

  13. QuantizeLinear và DequantizeLinear biểu diễn gì?
    QuantizeLinear: FP32 → INT8 bằng scale + zero_point. DequantizeLinear: INT8 → FP32 approximation.

  14. Vì sao TensorRT explicit quantization dùng Q/DQ graph?
    Scale encode trong graph, compiler fuse Q/DQ với op, precision boundary rõ ràng, hỗ trợ nhiều dtype.

  15. Vì sao không đưa calibration table vào model đã có Q/DQ nodes?
    Q/DQ đã có scale; external calibration table xung đột, override sai hoặc gây build lỗi.

  16. Per-channel quantization thường áp cho weights hay activations?
    Weights (per output channel); activations thường per-tensor.

  17. Layer nào thường nhạy với quantization?
    Softmax, LayerNorm, GELU, SiLU, attention score matmul, first/last layer, residual add nhỏ.

  18. INT8 accuracy collapse — debug theo thứ tự nào?
    Preprocessing → calibration data → calibration method → activation tensor comparison → exclude layer → QAT.

  19. INT8 chậm hơn FP16 — kiểm tra gì trước tiên?
    Layer profile → precision per layer → fallback nodes → Q/DQ count → có fuse không.

  20. FP8 không phải drop-in replacement cho INT8 — vì sao?
    FP8 cần hardware mới hơn (Hopper+), non-uniform spacing, scale khác, không phải mọi op có FP8 kernel tốt.

Summary

Quantization là kỹ thuật trung tâm của high-performance inference, nhưng không nên học như một flag hay recipe cố định. Bản chất gồm bốn lớp:

Lớp Nội dung
Numerical Scale, zero-point, rounding, clamping, outlier sensitivity
Graph QOperator, Q/DQ, placement, fusion, precision boundary
Runtime / compiler ONNX Runtime, TensorRT, kernel selection, fallback
Production Calibration data, accuracy validation, p99, fallback, monitoring

Workflow tốt nhất:

  1. FP32/FP16 baseline → đo accuracy + latency (không bỏ qua bước này)
  2. PTQ với calibration data đúng preprocessing
  3. Inspect Q/DQ graph (op counts, scale shapes)
  4. Benchmark latency + validate accuracy trên validation set thật
  5. Debug accuracy drop theo 8 bước có hệ thống
  6. Exclude sensitive layers / tune calibration method
  7. Nếu cần: QAT với same quant config như backend
  8. Build TensorRT engine → validate production constraints

Khi hiểu Lesson 5, các bài về Triton, dynamic batching và production rollout sẽ có nền tảng vững hơn: model artifact không chỉ là model.onnx hay model.plan, mà là artifact gắn với precision, scale, hardware, runtime và validation protocol.
