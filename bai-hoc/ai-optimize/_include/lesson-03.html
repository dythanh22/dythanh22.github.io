3.1 ONNX Runtime là gì — và không phải gì?

ORT chỉ “đọc file rồi chạy từng node”, hay còn làm gì trước khi inference?

Quan trọngÝ chính

ONNX = format/spec. ORT = engine (optimize + plan + dispatch + memory). Execution Provider = backend chạy op/subgraph trên hardware/library cụ thể. ORT ≠ TensorRT — ORT chỉ dùng TRT qua TensorRT EP; bản thân ORT không compile engine.

Pipeline khái niệm khi tạo session và chạy inference:

1. Load model          5. Partition graph by EP       9. Return outputs
2. Validate            6. Create execution plan
3. Resolve graph       7. Allocate/reuse memory
4. Graph optimizations 8. Dispatch kernels

Mental model: ORT = graph optimizer + execution planner + provider dispatcher + kernel runtime + memory manager.

Không phải Hệ quả thực tế
ONNX model.onnx = file format; onnxruntime = library chạy file đó
TensorRT CUDA EP dùng CUDA/cuDNN; TRT EP build engine cho subgraph hỗ trợ; native TRT = API trực tiếp
Luôn nhanh hơn PyTorch Model rất nhỏ / batch 1 / nhiều copy → PyTorch có thể ngang hoặc thắng nếu benchmark chưa thiết kế đúng

3.2 InferenceSession: đơn vị runtime trung tâm

Vì sao tạo InferenceSession trong mỗi request là anti-pattern nguy hiểm?

Quan trọngÝ chính

InferenceSession chịu load, optimize, khởi tạo EP, tạo execution plan, allocator và kernels. Chi phí này chỉ trả một lần và rất lớn — đặc biệt TRT EP có thể mất hàng giây đến phút build engine. Trong production: tạo một lần lúc startup, reuse mãi.

Ví dụ tối thiểu:

import onnxruntime as ort
import numpy as np

session = ort.InferenceSession(
    "model.onnx",
    providers=["CPUExecutionProvider"],
)
input_name = session.get_inputs()[0].name
x = np.random.randn(1, 3, 224, 224).astype(np.float32)
outputs = session.run(None, {input_name: x})

Anti-pattern — tạo session mỗi request:

def predict(x):                               # ❌ SAI
    session = ort.InferenceSession("model.onnx")
    return session.run(None, {"input": x})
    # mỗi call: parse ONNX + optimize + load weights + init EP + warmup

Đúng — session toàn cục, reuse:

session = ort.InferenceSession("model.onnx")  # ✓ một lần lúc startup

def predict(x):
    return session.run(None, {"input": x})    # ✓ chỉ inference

InferenceSession chịu trách nhiệm: load + validate model, apply graph optimizations, khởi tạo Execution Providers, tạo execution plan, quản lý memory allocator và kernel cache, thực hiện inference.

Inspect input/output metadata

Luôn inspect trước khi serve để biết đúng input name, shape, dtype:

print("Providers:", session.get_providers())

print("Inputs:")
for x in session.get_inputs():
    print("  name:", x.name, "| shape:", x.shape, "| type:", x.type)

print("Outputs:")
for y in session.get_outputs():
    print("  name:", y.name, "| shape:", y.shape, "| type:", y.type)

Output điển hình (static batch):

Inputs:
  name: images | shape: [1, 3, 224, 224] | type: tensor(float)
Outputs:
  name: logits | shape: [1, 1000]        | type: tensor(float)

Dynamic batch hiện như ['batch', 3, 224, 224] hoặc [None, 3, 224, 224]. Sai input name → Required inputs are missing from input feed.

MẹoChi phí session creation — con số thực tế

Session creation gồm: parse ONNX, optimize graph, load weights, init provider, warmup allocator và kernel cache. Với TRT EP: build engine hàng giây đến phút tuỳ model và GPU. Đo startup riêng với time.perf_counter() bao quanh InferenceSession(...) — không được gộp vào p99 serving latency.

3.3 Execution Providers, priority order và fallback

“Bật GPU” có nghĩa toàn bộ graph chạy trên GPU không?

Quan trọngÝ chính

EP chạy node/subgraph mà nó hỗ trợ — không nhất thiết toàn graph. Thứ tự providers = ưu tiên phân vùng. Phần không hỗ trợ fallback sang EP tiếp theo. Nhiều lần fallback GPU→CPU→GPU gây copy data, khiến “GPU session” chậm hơn CPU-only.

Execution Provider Mục tiêu
CPUExecutionProvider CPU kernels của ORT
CUDAExecutionProvider NVIDIA GPU — CUDA/cuDNN/cuBLAS
TensorrtExecutionProvider NVIDIA TensorRT: compile + chạy subgraph hỗ trợ
OpenVINOExecutionProvider Intel OpenVINO
DmlExecutionProvider DirectML (Windows)
CoreMLExecutionProvider Apple Core ML
ROCMExecutionProvider AMD ROCm

Provider priority order:

# Ưu tiên CUDA, fallback CPU
providers = ["CUDAExecutionProvider", "CPUExecutionProvider"]

# Đảo lại → CPU ưu tiên dù có GPU — thường là lỗi trong production
providers = ["CPUExecutionProvider", "CUDAExecutionProvider"]

# TRT → CUDA → CPU (pattern chuẩn có TRT)
providers = [
    "TensorrtExecutionProvider",
    "CUDAExecutionProvider",
    "CPUExecutionProvider",
]

Mental model: TRT nhận subgraph TRT hỗ trợ → CUDA nhận phần GPU còn lại → CPU nhận phần còn lại.

Graph partitioning và fallback:

ORT hỏi từng EP: “Bạn hỗ trợ node nào trong graph này?”. Provider trả lời; ORT phân vùng graph. Ví dụ graph detection:

Conv + Relu            → TensorRT EP (hoặc CUDA EP)
NonMaxSuppression      → CUDA EP hoặc CPU EP (không hỗ trợ TRT)

Nếu fallback xảy ra nhiều lần: GPU subgraph → copy về CPU → CPU op → copy lại GPU. Chi phí copy lặp lại có thể nuốt toàn bộ lợi thế GPU.

Cảnh báoVì sao GPU đôi khi chậm hơn CPU?
Nguyên nhân Hướng debug
Model/batch quá nhỏ — compute không bù overhead Tăng batch size
session.run(numpy) copy CPU→GPU→CPU mỗi lần Dùng I/O Binding
Nhiều op fallback về CPU Profiling trace + verbose log
Đo cả session creation (cold start) Tách startup time
Chưa warmup đủ Warmup ≥ 30 lần
Provider order sai Kiểm tra session.get_providers()
Preprocess/postprocess CPU dominate Tách ORT-only vs E2E
Dynamic shape khó reuse memory/engine Static shape khi có thể

Benchmark đúng phải tách: session creation | warmup | steady-state | data transfer | preprocessing | postprocessing.

3.4 SessionOptions: cấu hình runtime

Muốn bật profiling, lưu optimized graph hay giới hạn threads — cấu hình ở đâu?

Quan trọngÝ chính

SessionOptions là nơi cấu hình trước khi tạo session. Luôn set graph_optimization_level = ORT_ENABLE_ALL cho production. Set optimized_model_filepath khi muốn inspect hoặc lưu offline. Set enable_profiling khi debug performance.

import onnxruntime as ort

sess_options = ort.SessionOptions()
sess_options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
sess_options.execution_mode = ort.ExecutionMode.ORT_SEQUENTIAL
sess_options.intra_op_num_threads = 0            # 0 = ORT tự quyết
sess_options.inter_op_num_threads = 0
sess_options.enable_profiling = True
sess_options.profile_file_prefix = "ort_profile"
sess_options.optimized_model_filepath = "model_optimized.onnx"
sess_options.enable_cpu_mem_arena = True
sess_options.enable_mem_pattern = True

session = ort.InferenceSession(
    "model.onnx",
    sess_options=sess_options,
    providers=["CPUExecutionProvider"],
)
Option Ý nghĩa chi tiết
graph_optimization_level Disable / basic / extended / all — xem Mục 3.5
execution_mode ORT_SEQUENTIAL: tốt cho latency thấp; ORT_PARALLEL: khi graph có nhiều branch độc lập
intra_op_num_threads Thread parallelize bên trong một operator (MatMul, Conv); 0 = ORT tự quyết
inter_op_num_threads Thread parallelize giữa các operator khi dùng ORT_PARALLEL
enable_profiling Ghi JSON trace operator-level; kết hợp với profile_file_prefix
optimized_model_filepath Lưu optimized model ra file: inspect, so node count, reuse offline
enable_cpu_mem_arena Bật memory pool để giảm alloc/dealloc overhead
enable_mem_pattern Cho phép reuse memory pattern khi input shape ổn định

3.5 Graph optimization

ORT “optimize graph” nghĩa là biến đổi gì — và có bao nhiêu mức?

Quan trọngÝ chính

Graph optimization biến đổi graph để chạy nhanh hơn mà không đổi output semantics. Production luôn dùng ORT_ENABLE_ALL trừ khi có lý do đặc biệt. Lưu optimized model để inspect (Netron) và giảm startup latency (offline mode).

Ví dụ kinh điển:

Conv → BatchNorm → Relu      →  FusedConvBnRelu    (3 node → 1 kernel)
Constant → Add → Mul         →  SingleConstant      (constant folding)

Bốn mức optimization

Level Enum Bao gồm
Tắt ORT_DISABLE_ALL Không optimize — chỉ dùng khi debug
Basic ORT_ENABLE_BASIC Fold/fuse an toàn; chạy trước partitioning → áp dụng bất kể provider
Extended ORT_ENABLE_EXTENDED Basic + pattern kiến trúc phụ thuộc provider
All ORT_ENABLE_ALL Extended + layout optimizations (NCHW→NCHWc, …)

Basic optimizations (provider-agnostic, chạy trước partitioning):

  • Constant folding, identity elimination, dropout elimination
  • Conv + Add / Conv + BatchNorm fusion
  • Reshape fusion

Extended optimizations (fuse pattern kiến trúc, phụ thuộc provider nhiều hơn):

  • GELU fusion, LayerNorm fusion
  • Attention fusion, SkipLayerNorm fusion, BiasGELU fusion

Layout optimizations (chỉ trong ORT_ENABLE_ALL): đổi data layout phù hợp hardware (vd. NCHW → NCHWc trên CPU vectorized). Ít portable hơn — artifact tối ưu cho một máy có thể không tối ưu trên máy khác.

Online optimization vs offline optimization

Online (mặc định): ORT optimize lúc tạo session.

  • Ưu: dễ, luôn tối ưu theo environment hiện tại
  • Nhược: tăng startup latency; mỗi restart phải optimize lại

Offline: lưu optimized model ra disk để dùng lại.

sess_options = ort.SessionOptions()
sess_options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
sess_options.optimized_model_filepath = "model_optimized.onnx"

# Chạy một lần để tạo file
session = ort.InferenceSession(
    "model.onnx",
    sess_options=sess_options,
    providers=["CPUExecutionProvider"],
)
# => sinh ra model_optimized.onnx

# Lần sau load thẳng, startup nhanh hơn
session2 = ort.InferenceSession("model_optimized.onnx", providers=["CPUExecutionProvider"])

Ưu: giảm startup overhead; có thể inspect graph; so node count trước/sau. Nhược: artifact phụ thuộc provider/hardware/session options — không portable tự do.

Cảnh báoBẫy portability của optimized graph

GPU-optimized graph không nên assume chạy tốt trên CPU khác. Với TRT EP, engine cache/EP context có cơ chế riêng. Hãy coi optimized graph là artifact cho deployment cụ thể, không thay thế ONNX gốc.

MẹoĐào sâu: xem node count trước/sau optimize 
import onnx

def count_nodes(path):
    return len(onnx.load(path).graph.node)

print("Before:", count_nodes("model.onnx"))
print("After: ", count_nodes("model_optimized.onnx"))

BatchNorm fold, Conv fusion, identity elimination thường giảm rõ node count. Mở Netron để thấy trực quan pattern nào biến mất hoặc được gộp lại. Có thể thấy node thuộc domain đặc biệt của ORT (com.microsoft.*) thay thế pattern gốc.

3.6 Thread management trên CPU

Nhiều sessions song song — mỗi session nên dùng bao nhiêu thread?

Quan trọngÝ chính

ORT có hai loại thread parallelism: intra-op (bên trong một op) và inter-op (giữa các op độc lập). Khi nhiều sessions chạy đồng thời, giảm intra_op_num_threads để tránh oversubscription gây p99 biến động.

Intra-op parallelism — parallelize bên trong một operator:

options = ort.SessionOptions()
options.intra_op_num_threads = 4   # 4 thread cho một MatMul/Conv lớn

Inter-op parallelism — parallelize giữa các op độc lập trong graph:

options = ort.SessionOptions()
options.execution_mode = ort.ExecutionMode.ORT_PARALLEL
options.inter_op_num_threads = 2   # chạy song song branch A và B

Hữu ích khi graph có nhiều branch song song (vd. multi-head attention, multi-scale feature pyramid).

Tình huống Gợi ý
Đơn session, muốn max tốc độ Default (intra_op = 0)
Nhiều session song song Giảm intra_op tránh oversubscription: total_cores / num_sessions
Graph có nhiều branch độc lập Thử ORT_PARALLEL + inter_op_num_threads
Container bị giới hạn CPU quota Set intra_op khớp quota
p99 latency biến động cao Test thread affinity và spinning settings

Rule of thumb: bắt đầu với default, benchmark, rồi tune. Đừng tăng thread khi đã có nhiều sessions cùng chạy.

3.7 CUDA Execution Provider

CUDA EP cần cấu hình gì — và version mismatch xử lý ra sao?

Quan trọngÝ chính

CUDAExecutionProvider dùng NVIDIA GPU qua CUDA/cuDNN/cuBLAS. Package onnxruntime-gpu phải tương thích major version CUDA/cuDNN trong môi trường. Khi EP không load, dùng ort.print_debug_info() để chẩn đoán — không đoán mò.

Tạo session cơ bản:

session = ort.InferenceSession(
    "model.onnx",
    providers=["CUDAExecutionProvider", "CPUExecutionProvider"],
)

Cấu hình chi tiết:

providers = [
    (
        "CUDAExecutionProvider",
        {
            "device_id": 0,
            "arena_extend_strategy": "kNextPowerOfTwo",
            "gpu_mem_limit": 2 * 1024 * 1024 * 1024,  # 2 GB
            "cudnn_conv_algo_search": "EXHAUSTIVE",
            "do_copy_in_default_stream": True,
        },
    ),
    "CPUExecutionProvider",
]
session = ort.InferenceSession("model.onnx", providers=providers)
Option Ý nghĩa
device_id GPU index (0, 1, …)
gpu_mem_limit Giới hạn memory arena GPU (bytes)
arena_extend_strategy Cách tăng kích thước memory pool
cudnn_conv_algo_search EXHAUSTIVE: benchmark nhiều algo, chọn tốt nhất; DEFAULT: startup nhanh hơn
do_copy_in_default_stream Copy trên default CUDA stream hay stream riêng
use_tf32 TF32 trên Ampere+ cho FP32 matmul/conv
enable_cuda_graph CUDA Graph giảm CPU launch overhead (điều kiện: shape tĩnh, no conditional)

import torch

Nếu CUDA EP không xuất hiện:

3.8 TensorRT Execution Provider

Khi nào TensorRT EP đáng dùng — và engine cache hoạt động như thế nào?

Quan trọngÝ chính

TRT EP compile subgraph được hỗ trợ thành TensorRT engine — lần đầu rất chậm (build). Bật trt_engine_cache_enable để cache engine cho lần sau. TRT EP tiện nhưng không thay thế TensorRT native khi cần control sâu về profile, plugin, calibration, tactic.

providers = [
    (
        "TensorrtExecutionProvider",
        {
            "device_id": 0,
            "trt_fp16_enable": True,
            "trt_engine_cache_enable": True,
            "trt_engine_cache_path": "./trt_cache",
        },
    ),
    (
        "CUDAExecutionProvider",
        {"device_id": 0},
    ),
    "CPUExecutionProvider",
]
session = ort.InferenceSession("model.onnx", providers=providers)

Phân vùng graph:

ORT partition graph
  ├─ TRT-supported subgraphs   → TensorRT engine
  ├─ Unsupported GPU subgraphs → CUDA EP
  └─ Remaining nodes           → CPU EP

Khi nào dùng TensorRT EP:

Điều kiện Đủ điều kiện?
NVIDIA GPU deployment ✓
Model có nhiều op TRT hỗ trợ (Conv, MatMul, Attention…) ✓
Chấp nhận engine build time lần đầu ✓
Có thể cache và reuse engine ✓
Input shape ổn định hoặc có optimization profile ✓
Đã có CUDA EP baseline để so sánh ✓

Khi nào chưa nên dùng TensorRT EP:

Tình huống Lý do
ONNX model chưa sạch (shape inference thiếu) TRT fail hoặc fallback nhiều
Nhiều custom/unsupported ops Ít subgraph cho TRT, ít speedup
Chưa có CUDA EP baseline Không có baseline để so sánh
Chưa tách cold start khỏi warm latency Dễ nhầm engine build time với inference time
Dynamic shape rộng, chưa có profile rõ Engine rebuild liên tục

Engine cache:

trt_options = {
    "trt_engine_cache_enable": True,
    "trt_engine_cache_path": "./trt_cache",
    "trt_fp16_enable": True,
}

Sau lần đầu build, cache giúp startup nhanh hơn nhiều lần. Chú ý: nếu input shape nằm ngoài optimization profile đã cache, engine sẽ rebuild.

Cảnh báoTensorRT EP không thay thế TensorRT native

Khi cần control sâu — optimization profile, custom plugin, INT8 calibration, memory pool, CUDA stream, tactic selection, engine serialization, debugging tactic — bạn cần TensorRT native API (Lesson 4). TRT EP là convenience wrapper, không phải full TRT workflow.

MẹoĐào sâu: TRT vs CUDA EP — khi nào TRT thắng?

TRT build engine tối ưu cho GPU/model/precision cụ thể. Thường nhanh hơn CUDA EP 1.2–2.5× cho CNN/Transformer đủ lớn. Nhưng: - Build time: vài giây đến phút (dùng cache) - Portability: engine gắn với GPU architecture, TRT version, precision mode - Fallback overhead: phần TRT không hỗ trợ → copy sang CUDA/CPU → copy lại - Dynamic shape: cần optimization profile, ngoài range → rebuild

Nếu fallback nhiều và speedup thấp, xem xét simplify graph hoặc TRT native workflow.

3.9 I/O Binding và zero-copy mindset

session.run(numpy) đang copy dữ liệu bao nhiêu lần — và có thể tránh không?

Quan trọngÝ chính

Mặc định, session.run(numpy_input) copy CPU→GPU trước inference và GPU→CPU sau. Với model nhỏ hoặc output lớn, copy dominate latency chứ không phải compute. I/O Binding bind buffer trực tiếp trên device, loại bỏ copy không cần thiết.

Pipeline mặc định:

CPU numpy input  →  copy CPU→GPU  →  GPU compute  →  copy GPU→CPU  →  CPU numpy output

Zero-copy mindset — ideal production GPU pipeline:

preprocessing GPU  →  ORT input GPU  →  GPU compute  →  ORT output GPU  →  postprocess GPU
                                                              ↓
                                          copy kết quả gọn (scores, boxes) về CPU

Ví dụ vision serving: decode CPU → resize/normalize GPU → ORT input GPU → ORT output GPU → NMS GPU → copy compact result về CPU.

Copy tensor lớn về CPU quá sớm làm mất lợi thế GPU. Copy kết quả cuối cùng về CPU để trả response là bình thường — nhưng không nên copy intermediate tensors.

MẹoKhi nào I/O Binding đáng?
  • Model nhỏ / batch 1: khác biệt thường không đáng kể
  • Model hoặc output lớn: I/O Binding giảm overhead rõ ràng
  • Downstream cũng chạy GPU (NMS, decode, postprocess): giữ output trên GPU tránh copy thừa
  • Luôn so sánh session.run() vs run_with_iobinding() sau warmup để biết thực tế với model cụ thể

3.10 Profiling: đo đúng trước khi tối ưu

Làm thế nào biết latency nằm ở op nào — compute hay copy?

Quan trọngÝ chính

Không profiling thì rất dễ tối ưu sai chỗ. Bật enable_profiling để lấy JSON trace operator-level. Dùng Perfetto/Chrome tracing để visualize, tìm op dominate latency, copy overhead, hoặc fallback không ngờ.

Tách latency theo thành phần trước khi profile:

Thành phần Ví dụ
Session creation Load, optimize, build TRT engine
Warmup Lazy init, kernel cache, allocator growth
Input copy CPU → GPU
Compute Conv/MatMul/Attention kernels
Output copy GPU → CPU
Postprocessing NMS, decode, threshold
Queueing Request chờ batch hoặc worker

3.11 Benchmark methodology

Average latency 3 ms đã đủ để deploy production chưa?

Quan trọngÝ chính

Benchmark đúng cần: môi trường cố định, artifact cố định, warmup đủ, p50/p90/p99 (không chỉ average), batch sweep, và tách ORT-only vs end-to-end. p99 quan trọng hơn average vì trong production, 1% request chậm là điều user cảm nhận.

Fixed environment — ghi lại trước khi benchmark:

CPU model · GPU model · RAM
Driver · CUDA · cuDNN · TensorRT version
ONNX Runtime version · Python version · OS

Fixed model artifact — ghi lại:

model name · opset version · input shape
precision (FP32/FP16/INT8) · dynamic/static shape
optimization level · provider list và options

Warmup:

# Loại bỏ: lazy init, kernel cache, allocator growth, cold kernel selection
for _ in range(30):
    session.run(None, inputs)

Không tính warmup vào steady-state. Với TRT EP: lần đầu = engine build — cần warmup riêng sau khi cache đã load.

Percentile latency:

def percentile(values, p):
    values = sorted(values)
    k = int(round((len(values) - 1) * p / 100))
    return values[k]

# Đo: mean, p50, p90, p95, p99, min, max, throughput

Average có thể đẹp nhưng p99 xấu. p99 tệ = user cảm thấy lag 1 trong 100 request.

Batch size sweep:

Batch Mean ms p99 ms Throughput samples/s
1 — — —
4 — — —
8 — — —
16 — — —
32 — — — 
throughput = batch_size / (mean_ms / 1000)

Batch nhỏ → latency thấp, GPU util thấp. Batch lớn → throughput cao, per-request latency tăng.

Tách preprocessing / postprocessing:

ORT-only latency     = session.run() thuần — loại trừ data prep
end-to-end latency   = preprocess + ORT + postprocess

Khi debug, không trộn lẫn. “ORT chậm” đôi khi thực ra là preprocess CPU dominate.

3.13 Debug case studies

Khi inference có vấn đề, chẩn đoán như thế nào?

Quan trọngÝ chính

Bốn case study thường gặp nhất: (1) CUDA EP không load, (2) GPU chậm hơn CPU, (3) TRT build cực chậm lần đầu, (4) TRT ít speedup. Mỗi case có checklist riêng — đừng đoán, hãy đo.

Case 1 — CPU OK, CUDA lỗi hoặc không xuất hiện

Triệu chứng: CPUExecutionProvider OK; CUDAExecutionProvider không có trong get_available_providers() hoặc lỗi khi tạo session.

Nguyên nhân phổ biến:

  1. Cài onnxruntime (CPU) thay vì onnxruntime-gpu
  2. CUDA/cuDNN runtime không tương thích version
  3. Driver NVIDIA không đủ mới
  4. Môi trường thiếu shared libraries (libcudart, libcudnn)
  5. Container không expose GPU (--gpus all thiếu)
  6. Dùng sai Python venv

Checklist debug:

import onnxruntime as ort
print(ort.__version__)
print(ort.get_available_providers())
ort.print_debug_info()                 # in loading log đầy đủ
nvidia-smi                             # kiểm tra driver và GPU
pip show onnxruntime onnxruntime-gpu   # chỉ một trong hai

Không nên cài lẫn cả hai package cùng venv. Tạo venv mới sạch thường nhanh hơn debug dependency rối.

Case 2 — CUDA chậm hơn CPU

Triệu chứng:

CPU: 3 ms
CUDA: 7 ms
Nguyên nhân Kiểm tra Fix
Model/batch quá nhỏ Thử batch 8/16 Tăng batch size

Case 3 — TensorRT EP lần đầu cực chậm

Triệu chứng:

Session creation / first run: hàng giây đến phút
Steady-state sau đó: nhanh

Đây là bình thường — TensorRT cần build engine. Không nhầm build time với inference latency.

Giải pháp:

trt_options = {
    "trt_engine_cache_enable": True,
    "trt_engine_cache_path": "./trt_cache",
}

Sau lần đầu build, cache giúp startup nhanh. Chú ý: nếu input shape nằm ngoài optimization profile đã cache, engine có thể rebuild.

Case 4 — TensorRT EP ít hoặc không speedup

Triệu chứng:

Có TRT EP nhưng speedup so CUDA EP thấp
Profiling: nhiều node chạy CUDA EP hoặc CPU EP

Nguyên nhân:

  • Operator không được TRT hỗ trợ (data-dependent shape, custom op)
  • Shape inference thiếu → TRT không partition được nhiều
  • Dynamic shape phức tạp, profile chưa phù hợp
  • Graph có pattern không TRT-friendly (nhiều reshape/topk xen kẽ)

Giải pháp theo thứ tự:

  1. Chạy onnx.shape_inference.infer_shapes() trước khi dùng TRT EP
  2. Simplify graph bằng onnx-simplifier nếu phù hợp
  3. Kiểm tra log unsupported ops
  4. Viết TRT plugin nếu op cụ thể quan trọng
  5. Chấp nhận CUDA fallback cho phần còn lại
  6. Nếu cần control sâu → TensorRT native workflow (Lesson 4)

3.14 Common mistakes

Những lỗi nào lặp đi lặp lại nhất khi mới làm inference engineering?

Quan trọngÝ chính

Tám lỗi phổ biến, đều phòng tránh được bằng thói quen: chỉ định providers rõ, đúng order, reuse session, warmup, đo p99, cast float32, hiểu output copy, tách cold start TRT.

# Lỗi Hậu quả Fix
1 Không chỉ định providers Dựa vào default không kiểm soát Luôn truyền providers=[…] rõ ràng
2 Provider order sai: ["CPU…", "CUDA…"] CPU ưu tiên dù có GPU GPU provider đứng đầu
3 Tạo session trong predict() Mỗi request gánh overhead khởi tạo Session toàn cục, reuse
4 Benchmark không warmup Cold run không đại diện steady-state Warmup ≥ 30 lần trước khi đo
5 Chỉ đo average latency p99 có thể xấu dù mean đẹp Đo mean/p50/p90/p99/min/max
6 NumPy dtype float64 ORT phải convert, overhead và sai kết quả .astype(np.float32)
7 Quên output đang copy về CPU Mất lợi thế GPU khi downstream cũng GPU I/O Binding hoặc kiểm tra device_name()
8 So TRT cold start với CUDA warm run TRT “thua” vì đang build engine Tách startup vs steady-state

3.15 Production pattern và checklist

Service production tối thiểu trông như thế nào — và deploy cần kiểm gì?

Quan trọngÝ chính

Pattern tối thiểu: reuse session, explicit providers, ORT_ENABLE_ALL, warmup tại startup, validate dtype. Đã đủ cho phần lớn use case. Thêm I/O Binding và batching khi cần throughput cao hơn.

import numpy as np
import onnxruntime as ort


class OrtModel:
    def __init__(self, model_path: str):
        options = ort.SessionOptions()
        options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL

        self.session = ort.InferenceSession(
            model_path,
            sess_options=options,
            providers=self._select_providers(),
        )
        self.input_name = self.session.get_inputs()[0].name
        self.output_names = [x.name for x in self.session.get_outputs()]
        self._warmup()

    def _select_providers(self):
        avail = ort.get_available_providers()
        if "TensorrtExecutionProvider" in avail:
            return [
                ("TensorrtExecutionProvider", {
                    "trt_fp16_enable": True,
                    "trt_engine_cache_enable": True,
                    "trt_engine_cache_path": "./trt_cache",
                }),
                "CUDAExecutionProvider",
                "CPUExecutionProvider",
            ]
        if "CUDAExecutionProvider" in avail:
            return ["CUDAExecutionProvider", "CPUExecutionProvider"]
        return ["CPUExecutionProvider"]

    def _warmup(self):
        # Thay shape theo model thật
        x = np.random.randn(1, 3, 224, 224).astype(np.float32)
        for _ in range(10):
            self.session.run(self.output_names, {self.input_name: x})

    def predict(self, x: np.ndarray) -> list:
        if x.dtype != np.float32:
            x = x.astype(np.float32)
        return self.session.run(self.output_names, {self.input_name: x})

Pattern này chưa xử lý batching, concurrency hay I/O Binding — nhưng đúng ở mức căn bản: reuse session, explicit providers, optimization, warmup, validate dtype.

Lab 3 — Benchmark latency đúng cách

Tạo benchmark_ort.py:

import time
import numpy as np
import onnxruntime as ort


def percentile(values, p):
    values = sorted(values)
    k = int(round((len(values) - 1) * p / 100))
    return values[k]


def benchmark(session, input_name, x, warmup=30, repeat=200):
    # Warmup: bỏ qua lazy init, cache, allocator, kernel selection
    for _ in range(warmup):
        session.run(None, {input_name: x})

    latencies_ms = []
    for _ in range(repeat):
        start = time.perf_counter()
        session.run(None, {input_name: x})
        end = time.perf_counter()
        latencies_ms.append((end - start) * 1000)

    return {
        "mean_ms": sum(latencies_ms) / len(latencies_ms),
        "p50_ms":  percentile(latencies_ms, 50),
        "p90_ms":  percentile(latencies_ms, 90),
        "p99_ms":  percentile(latencies_ms, 99),
        "min_ms":  min(latencies_ms),
        "max_ms":  max(latencies_ms),
    }


def make_session(model_path, providers):
    options = ort.SessionOptions()
    options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
    return ort.InferenceSession(
        model_path,
        sess_options=options,
        providers=providers,
    )


model_path = "toy_cnn.onnx"
batch_size = 1
x = np.random.randn(batch_size, 3, 224, 224).astype(np.float32)

provider_sets = [["CPUExecutionProvider"]]

available = ort.get_available_providers()
if "CUDAExecutionProvider" in available:
    provider_sets.append(["CUDAExecutionProvider", "CPUExecutionProvider"])
if "TensorrtExecutionProvider" in available:
    provider_sets.append([
        "TensorrtExecutionProvider",
        "CUDAExecutionProvider",
        "CPUExecutionProvider",
    ])

for providers in provider_sets:
    print("=" * 60)
    print("Providers:", providers)
    session = make_session(model_path, providers)
    input_name = session.get_inputs()[0].name
    result = benchmark(session, input_name, x)
    for k, v in result.items():
        print(f"  {k}: {v:.3f}")

Lab 6 — I/O Binding với CUDA

Cần CUDAExecutionProvider. Tạo iobinding_cuda.py:

import time
import numpy as np
import onnxruntime as ort


if "CUDAExecutionProvider" not in ort.get_available_providers():
    raise RuntimeError("CUDAExecutionProvider is not available.")

session = ort.InferenceSession(
    "toy_cnn.onnx",
    providers=["CUDAExecutionProvider", "CPUExecutionProvider"],
)

input_name = session.get_inputs()[0].name
output_name = session.get_outputs()[0].name

x_cpu = np.random.randn(1, 3, 224, 224).astype(np.float32)

# Copy input vào OrtValue trên CUDA device 0
x_gpu = ort.OrtValue.ortvalue_from_numpy(x_cpu, "cuda", 0)

io_binding = session.io_binding()

io_binding.bind_input(
    name=input_name,
    device_type=x_gpu.device_name(),
    device_id=0,
    element_type=np.float32,
    shape=x_gpu.shape(),
    buffer_ptr=x_gpu.data_ptr(),
)

# Yêu cầu ORT allocate output trên GPU
io_binding.bind_output(
    name=output_name,
    device_type="cuda",
    device_id=0,
)

# Warmup
for _ in range(20):
    session.run_with_iobinding(io_binding)

latencies = []
for _ in range(100):
    start = time.perf_counter()
    session.run_with_iobinding(io_binding)
    end = time.perf_counter()
    latencies.append((end - start) * 1000)

outputs_gpu = io_binding.get_outputs()
print("Output device:", outputs_gpu[0].device_name())
print("Mean latency ms:", sum(latencies) / len(latencies))

# Chỉ copy về CPU khi thật sự cần
y_cpu = outputs_gpu[0].numpy()
print("Output shape:", y_cpu.shape)

  2. Optimization levels: benchmark 4 level + node count: DISABLE_ALL / BASIC / EXTENDED / ALL
  3. Batch sweep: bảng mean/p99/throughput với batch 1/4/8/16/32; throughput = batch / (mean_ms / 1000)
  4. Profile analysis: op chậm nhất? có event copy? overhead ở compute hay nơi khác?
  5. (GPU) I/O Binding: so session.run() vs run_with_iobinding() nhiều batch size
  6. (GPU) TRT EP: CUDA baseline → TRT no-cache → TRT với cache; tách session creation time vs steady-state latency

Checkpoint questions

MẹoTự kiểm — trả lời thử trước khi mở
  1. ONNX vs ONNX Runtime? Format/spec vs engine chạy model.
  2. Session init làm gì? Load, validate, optimize, init EP, plan, memory/kernels.
  3. Vì sao không tạo session mỗi request? Chi phí khởi tạo lớn; TRT build hàng giây–phút.
  4. Execution Provider là gì? Backend chạy node/subgraph trên hardware/library cụ thể.
  5. Provider order ảnh hưởng gì? Quyết định EP nào nhận subgraph; sai order → CPU ưu tiên dù có GPU.
  6. Graph partitioning là gì? ORT hỏi từng EP về capability → chia graph thành subgraph.
  7. Fallback làm GPU chậm thế nào? Copy GPU→CPU→GPU lặp nhiều lần — copy overhead.
  8. Basic vs extended optimize? Basic: fold/fuse an toàn, trước partitioning. Extended: pattern kiến trúc (GELU/Attention), phụ thuộc provider.
  9. Online vs offline optimize? Online: mỗi session init. Offline: lưu file, startup nhanh, kém portable hơn.
  10. Intra-op vs inter-op threads? Bên trong một op vs giữa nhiều op song song trong graph.
  11. CUDA chậm hơn CPU khi nào? Model/batch nhỏ, copy mỗi run, fallback, cold start, provider order sai.
  12. I/O Binding giải quyết gì? Loại bỏ copy CPU↔︎GPU bằng cách bind buffer trực tiếp trên device.
  13. TRT lần đầu chậm — tại sao? Build TensorRT engine. Fix: engine cache.
  14. Engine cache dùng để làm gì? Lưu TRT engine để lần sau không rebuild; shape ngoài profile → rebuild.
  15. Benchmark cần metric nào? Warmup + p50/p90/p99 + throughput; tách ORT-only vs E2E.

Summary

  1. ORT = engine: optimize graph → partition → dispatch → memory. Không chỉ “chạy từng node”.
  2. Session reuse: session creation tốn kém (đặc biệt TRT) — tạo một lần lúc startup.
  3. Provider order = priority: sai order → CPU ưu tiên dù có GPU. Luôn kiểm tra session.get_providers().
  4. Fallback = copy overhead: GPU session chậm hơn CPU thường do copy CPU↔︎GPU lặp — không phải compute.
  5. ORT_ENABLE_ALL: luôn bật cho production; offline mode giảm startup overhead.
  6. Profiling trước khi tune: không biết bottleneck thì tối ưu sai chỗ. Dùng JSON trace + Perfetto.
  7. p99 quan trọng hơn average trong production — average đẹp chưa đủ.
  8. TRT EP: tiện nhưng có build cost → engine cache; không thay thế TensorRT native (Lesson 4).
