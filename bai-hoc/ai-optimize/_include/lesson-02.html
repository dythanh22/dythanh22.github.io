2.1 ONNX là gì — và không phải gì?

ONNX chỉ là file .onnx được export, hay là một chuẩn biểu diễn computation graph?

Quan trọngÝ chính

ONNX (Open Neural Network Exchange) là chuẩn mở: computation graph + metadata + weights + I/O schema + operator set. Nó không phải runtime, không tự làm model nhanh hơn, và không thay evaluation số học.

Một model PyTorch khi export sang ONNX không lưu Python code forward(). Chỉ còn graph mà runtime khác đọc được:

class MLP(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = torch.nn.Linear(4, 8)
        self.fc2 = torch.nn.Linear(8, 2)

    def forward(self, x):
        x = torch.relu(self.fc1(x))
        return self.fc2(x)

Sau export, graph trông giống Input → Gemm → Relu → Gemm → Output. Code Python biến mất; thứ còn lại là biểu diễn mà runtime khác đọc được.

ONNX không phải Hệ quả
Runtime Cần ORT, TensorRT, OpenVINO, CoreML, TVM, … để chạy
Đảm bảo nhanh hơn Tốc độ phụ thuộc backend, ops, shape, batch, dtype, transfer
Đảm bảo mọi PyTorch export được Control flow, custom ops, data-dependent shape dễ fail hoặc bị specialize
Thay evaluation Schema hợp lệ ≠ tương đương số học với model gốc
MẹoĐào sâu: bốn điều ONNX không đảm bảo

1. Không phải runtime. Muốn chạy ONNX model cần runtime/compiler: ONNX Runtime, TensorRT, OpenVINO, CoreML, TVM, hoặc backend riêng của hardware vendor.

2. Không tự đảm bảo nhanh hơn. Export PyTorch sang ONNX không tự làm model nhanh hơn. Tốc độ phụ thuộc vào runtime, operator coverage, graph optimization, hardware, static/dynamic shape, batch size, memory transfer, và dtype (FP32/FP16/BF16/INT8).

3. Không đảm bảo mọi PyTorch model export được. PyTorch linh hoạt hơn ONNX rất nhiều. Python control flow, custom ops, data-dependent shape logic, tensor-to-Python conversion có thể gây lỗi hoặc bị specialize thành shape cố định.

4. Không thay evaluation. ONNX schema hợp lệ chưa chứng minh output đúng. Luôn so sánh output giữa framework gốc và ONNX Runtime với cùng input test.

Pipeline tối thiểu để tin một file .onnx: (1) onnx.checker.check_model, (2) chạy ORT CPU với cùng input, (3) assert_allclose với PyTorch. Ba bước này bắt hầu hết lỗi “export OK nhưng sai”.

2.2 Cấu trúc một ONNX model

File .onnx thực chất chứa những lớp protobuf nào?

Quan trọngÝ chính

File .onnx là ModelProto đã serialize. Phần lõi là GraphProto: node[] + edges (tên tensor) + initializer[] (weights) + input[] / output[].

ModelProto
  |-- ir_version, producer_*, domain, model_version, doc_string
  |-- opset_import[]
  |-- GraphProto
        |-- name, input[], output[], initializer[], value_info[], node[]
Thành phần Ý nghĩa
ModelProto Container cấp cao
GraphProto Computation graph chính
NodeProto Một phép tính (Conv, Relu, MatMul, …)
TensorProto Tensor serialize (thường weights/constant)
ValueInfoProto Tên, dtype, shape của value
opset_import Operator set version đang dùng
initializer Named tensors cố định — thường parameters

Mental model: Graph = nodes + edges; Node = operator call; Edge = named tensor; Weights = initializer.

Graph là dataflow, không phải dòng lệnh tuần tự. ONNX graph biểu diễn computation theo kiểu dataflow có hướng: mỗi node tiêu thụ input tensor và tạo output tensor. Node không có side effect — không biến toàn cục, không đọc/ghi state ngoài tensor. Các node sắp xếp theo topological order: node cần output của node khác sẽ xuất hiện sau. Ví dụ node Conv:

op_type: Conv
inputs:  ["images", "conv.weight", "conv.bias"]
outputs: ["conv_out"]
attributes: strides=[1,1], pads=[1,1,1,1]
MẹoĐào sâu: GraphProto fields bạn sẽ inspect
  • input[] / output[]: public I/O — tên, dtype, shape mà runtime cần cung cấp/nhận
  • value_info[]: metadata intermediate tensors — thường đầy hơn sau onnx.shape_inference.infer_shapes
  • initializer[]: weights/constants — runtime load từ file .onnx, user không truyền mỗi request
  • node[]: danh sách operator calls theo topological order

2.3 Tensor, node, operator và domain

conv.weight trong graph là input runtime hay weight đã lưu sẵn?

Quan trọngÝ chính

Tensor nối node bằng name. Operator = định nghĩa phép toán; node = một lần dùng operator. Attribute là cấu hình tĩnh (strides, pads); input là tensor thay đổi theo request. Initializer thường là weights — đừng nhầm với runtime input.

Trong ONNX, tensor được nhận diện bằng tên. Hai node dùng cùng tên tensor nghĩa là chúng được nối với nhau:

Node A outputs: ["hidden_1"]
Node B inputs:  ["hidden_1"]

Bốn loại tensor trong graph.

Loại Vai trò Ví dụ
Graph input User/runtime cung cấp khi infer images: float32[batch,3,224,224]
Graph output Runtime trả về logits: float32[batch,1000]
Intermediate Giữa các node, không public conv_out → relu_out → pool_out
Initializer Giá trị cố định trong model conv.weight, fc.bias

Initializer thường là weights và bias. Runtime load chúng từ file .onnx — user không cần (và không nên) truyền vào mỗi request.

Cảnh báoBẫy thường gặp: initializer ≠ runtime input

Thấy conv.weight trong graph rồi truyền như runtime input là sai. Nếu tensor nằm trong initializer[], runtime đã load nó từ file .onnx. Nhiều bạn mới học nhầm điều này khi viết serving code.

Operator vs node — distinction rất quan trọng.

Operator = định nghĩa phép toán
Node     = một lần sử dụng operator trong graph

Operator Relu: y = max(0, x)

Graph có thể có ba node cùng op_type = "Relu":
  relu1: Relu(conv1_out) → relu1_out
  relu2: Relu(conv2_out) → relu2_out
  relu3: Relu(fc1_out)   → relu3_out

Ba node này dùng cùng operator spec, nhưng là ba lần gọi khác nhau với I/O khác nhau.

Anatomy của NodeProto.

Field Ý nghĩa
op_type Conv, Relu, MatMul, …
domain Namespace (ai.onnx, ai.onnx.ml, custom)
input[] Tên tensor đầu vào
output[] Tên tensor đầu ra
attribute[] Tham số tĩnh của operator
name Tên node (tuỳ chọn)

Attribute khác input. Input là tensor thay đổi theo request; attribute là cấu hình tĩnh không đổi giữa các request.

Ví dụ với Conv:

Inputs (tensor, thay đổi theo request):
  X  — input feature map
  W  — weight tensor
  B  — optional bias tensor

Attributes (cấu hình tĩnh):
  strides, pads, dilations, groups

Operator domain. ONNX dùng domain để phân biệt operator sets.

Domain Ý nghĩa
ai.onnx / "" Standard ops (Conv, Relu, MatMul, …)
ai.onnx.ml Classical ML ops (LinearRegressor, …)
Custom Operator riêng của framework/vendor/user

Custom domain gây lỗi phổ biến: No Op registered for CustomFoo with domain_version of X (ORT) hoặc Unsupported operator: CustomFoo (TensorRT). Production nên ưu tiên standard ONNX ops nếu cần portable qua nhiều backend.

2.4 Opset và các loại version

Vì sao export opset mới nhất lại làm TensorRT/ORT fail?

Quan trọngÝ chính

Opset (operator set) = version của operator specifications. Chọn opset theo backend target, không theo “mới nhất”. ir_version ≠ opset_import.version ≠ model_version — ba khái niệm hoàn toàn khác nhau.

Vì sao cần opset? Operator không bất biến mãi mãi. Theo thời gian, semantics, type support, shape inference rule của operator có thể thay đổi. Add, Resize, Slice, Gather, Softmax — mỗi operator có thể có spec ở nhiều version. Graph cần khai báo: “Tôi đang dùng operator theo version nào?”

opset_import:
  domain: ""
  version: 18

Nghĩa là domain mặc định (ai.onnx) dùng standard opset 18.

Quy tắc tư duy. Khi graph có opset N, mỗi operator dùng định nghĩa mới nhất có version ≤ N.

Graph opset = 15
Operator Add có spec ở version 7, 13, 14
=> Node Add trong graph dùng Add-14 semantics

Không phải opset mới nhất là tốt nhất. Trong production, phải chọn opset theo backend target:

PyTorch exporter hỗ trợ opset A
ORT version đang deploy hỗ trợ opset B
TensorRT parser đang deploy hỗ trợ opset C
Model dùng ops D
=> chọn opset đủ mới để biểu diễn model,
   đủ cũ để backend stable

Nếu opset quá mới: runtime/compiler chưa hỗ trợ. Nếu quá cũ: exporter không biểu diễn được behavior mong muốn.

Phân biệt các loại version.

Version Ý nghĩa
IR version Format/cấu trúc biểu diễn graph
Opset version Spec của operators
Model version Do tác giả đặt (quản lý artifact)
Package onnx Version Python package (onnx==1.x)
MẹoChecklist khi chọn opset cho production
  1. In model.opset_import của model đã export
  2. Đối chiếu release notes ORT version đang deploy
  3. Đối chiếu TRT version đang deploy (support matrix chính thức)
  4. Chạy checker + ORT CPU + (nếu có) TRT parse trên đúng version đó — không chỉ máy dev mới nhất

Không commit “opset 22 vì đó là mới nhất” nếu TRT phiên bản cũ hơn chưa hỗ trợ đầy đủ.

2.5 Shape, dtype và layout

Dynamic mọi dimension có phải lúc nào cũng tốt hơn static?

Quan trọngÝ chính

Shape/dtype/layout là nguồn lỗi lớn nhất khi export và serve. Dynamic chỉ những chiều thật sự cần; layout sai (NCHW vs NHWC) có thể không crash mà cho output sai im lặng.

Static vs dynamic shape.

Static Dynamic
Ví dụ float32[1,3,224,224] float32[batch,3,224,224]
Ưu Tối ưu dễ, TRT build/memory planning đơn giản Linh hoạt batch/serving
Nhược Đổi batch/size → fail Khó tối ưu; TRT cần min/opt/max profile

Không phải mọi thứ cần dynamic. Image classifier phục vụ ảnh đã resize về 224×224 nên dùng [batch,3,224,224], không phải [batch,channel,height,width]. Height/width dynamic không cần thiết làm performance và debug tệ hơn. TRT cần profile, ORT khó tối ưu hơn.

Dtype phổ biến.

Dtype Dùng phổ biến cho
float32 Inference mặc định
float16 GPU inference, TRT FP16
bfloat16 Training, một số inference mới
int64 Token IDs, long indices
int32 Counters, short indices
bool Masks, attention
string NLP tokenizer output (hiếm trong ONNX)

Sai dtype (ví dụ int32 thay int64 cho input_ids) → ORT báo lỗi rõ ràng tại runtime. Với NLP, tokenizer có thể tạo int64 hoặc int32 tùy framework — luôn inspect input dtype của ONNX graph trước khi viết serving code.

NCHW vs NHWC — silent mismatch.

NCHW = [N, C, H, W]   # PyTorch conv thường dùng
NHWC = [N, H, W, C]   # hay gặp TF/Keras

Lỗi layout rất nguy hiểm vì đôi khi không crash. Nếu số chiều khớp tình cờ, runtime không báo lỗi nhưng output sai hoàn toàn. Ví dụ truyền [1, 224, 224, 3] (NHWC) vào model kỳ vọng [1, 3, 224, 224] (NCHW) — shape check có thể pass nếu channel=3 bằng height tình cờ, nhưng inference hoàn toàn sai.

Checklist trước serving: input name · dtype · shape · NCHW/NHWC · mean/std · RGB/BGR.

MẹoĐào sâu: dynamic shape và TensorRT profile

Dynamic batch thường kèm profile cho TensorRT (Lesson 4 sẽ đi sâu):

min shape: [1,  3, 32, 32]
opt shape: [8,  3, 32, 32]
max shape: [64, 3, 32, 32]

TRT tối ưu engine dựa trên khoảng shape này. Shape ngoài profile → inference có thể fail hoặc fallback không tối ưu. Điều này là lý do chỉ dynamic những dimension thật sự cần.

2.6 Export pipeline từ PyTorch

Export ONNX khác torch.save(state_dict) ở điểm nào?

Quan trọngÝ chính

Export = capture/normalize/translate graph + weights, không chỉ lưu weights. Cần example input, model.eval(), và luôn numerical validate với runtime sau export.

Vì sao cần example input? PyTorch model là Python program. Exporter cần chạy/capture model với example input để biết computation graph nào được tạo. Example input giúp exporter: biết dtype, biết rank/số chiều tensor, trace/capture tensor operations, suy luận shape constraints, và specialize một số nhánh logic nếu cần.

Vì sao cần model.eval()? Một số layer có behavior khác nhau giữa training và inference: Dropout (random zeros training, pass-through inference), BatchNorm (batch stats training, running stats inference), và các module có conditional behavior theo self.training. Export khi model ở training mode cho graph sai cho inference.

model.eval()
with torch.no_grad():
    ...  # export

Export ≠ save weights.

Artifact Lưu gì? Chạy ngoài PyTorch?
.pth state dict Weights Không — cần Python class
TorchScript Graph/module PyTorch Có, trong ecosystem PyTorch
ONNX Graph trung lập + weights Có nếu runtime hỗ trợ ops
TensorRT engine Engine tối ưu GPU cụ thể Có, phụ thuộc TRT/GPU/platform
MẹoPreview: ONNX Runtime và graph optimization

ONNX Runtime load graph → optimize → gán subgraph cho Execution Provider → execute.

Execution Providers (EP): CPUExecutionProvider, CUDAExecutionProvider, TensorrtExecutionProvider, OpenVINOExecutionProvider, CoreMLExecutionProvider. Khi dùng nhiều EP, runtime cố gán subgraph cho provider chuyên biệt rồi fallback nếu cấu hình cho phép.

Bốn loại graph optimization ORT thực hiện (giữ nguyên semantics):

  • Constant folding: subgraph chỉ phụ thuộc constant/initializer → tính trước, thay bằng constant
  • Dead node elimination: node tạo output không được dùng → loại bỏ
  • Identity elimination: x → Identity → y không cần thiết → gộp trực tiếp
  • Operator fusion: Conv → BN → Relu → fuse thành một kernel tối ưu hơn

Chi tiết EP và tuning → Lesson 3.

2.7 Validate, lỗi phổ biến và debug

onnx.checker pass đã đủ để tin model chưa?

Quan trọngÝ chính

Checker chỉ nói schema hợp lệ. Luôn so PyTorch vs ORT trên cùng input. ONNX Runtime chạy được không đảm bảo TensorRT build được — mỗi backend có operator coverage riêng.

Numerical validation — tolerance theo task type. Khác biệt floating point, fused kernel, backend optimization có thể làm output lệch nhỏ.

Task Tolerance gợi ý Metric thêm
Classification (FP32) rtol=1e-4, atol=1e-5 Top-1/Top-k, accuracy trên val set
Classification (FP16) rtol=1e-2, atol=1e-3 Top-1/Top-k
Object detection Metric-level mAP, NMS output, bbox tolerance
Segmentation Metric-level IoU, Dice
NLP embedding Cosine similarity Cosine > 0.999
ASR WER —
INT8 Metric-level, không element-wise Accuracy drop ≤ ngưỡng chấp nhận

Lỗi export phổ biến.

Vấn đề Triệu chứng Hướng xử lý
Shape bị fixed Muốn batch dynamic nhưng input [1,3,…] Kiểm tra dynamic_shapes / key argument forward / tránh x.shape[0] → Python control flow
Unsupported op Export hoặc runtime/TRT fail Tìm op, refactor sang op phổ biến, đổi opset, custom symbolic/plugin
Data-dependent control flow if x.sum() > 0 Refactor tensor ops / torch.where; tránh .item() / NumPy trong forward
Training mode Output lệch inference model.eval()
Dtype mismatch Actual int32, expected int64 astype / sửa tokenizer-preprocess
External data Model lớn, thiếu .onnx.data Copy đủ graph + external tensors khi deploy
MẹoĐào sâu: từng loại lỗi export — cách suy nghĩ

Shape bị fixed ngoài ý muốn. Nguyên nhân thường gặp: không set dynamic_shapes, dùng sai key (key là tên argument forward, không phải ONNX input name “images”), dùng x.shape[0] rồi đưa vào Python control flow, có logic làm exporter chứng minh dimension chỉ có một giá trị. Debug: inspect graph input shape bằng Python hoặc Netron, kiểm tra tên argument trong forward(), thử chạy ORT với batch size khác.

Unsupported operator. Tìm operator gây lỗi → kiểm tra có ONNX equivalent không → refactor sang op phổ biến → thử opset khác nếu operator support phụ thuộc opset → cân nhắc custom symbolic/ONNX Script/backend plugin.

Python control flow phụ thuộc tensor value.

# Nguy hiểm — exporter không biểu diễn được
def forward(self, x):
    if x.sum() > 0:
        return x * 2
    return x - 2

# Refactor thành tensor operation
def forward(self, x):
    return torch.where(x.sum() > 0, x * 2, x - 2)

.item(), .tolist(), NumPy conversion trong forward đưa tensor value sang Python scalar — làm graph capture khó hoặc value bị constant-fold theo example input.

Quy tắc: không dùng tensor value để điều khiển Python logic trong forward nếu muốn export portable.

Training mode khi export. Dropout còn active; BatchNorm dùng batch statistics thay running statistics. Luôn gọi model.eval() và so sánh numerical output sau export.

Dtype mismatch khi chạy runtime.

# Sửa numpy input
inputs = inputs.astype(np.int64)
# hoặc sửa tokenizer/preprocessing để tạo đúng dtype

External data cho model lớn. ONNX model vượt giới hạn hoặc cần tách weights → exporter lưu weights ra file ngoài. Khi deploy phải copy đủ model.onnx + model.onnx.data (hoặc tất cả external tensor files). Thiếu external data → runtime không load được model.

Cảnh báoCase study: ORT OK, TensorRT FAIL

Tình huống rất phổ biến: PyTorch export OK → ORT CPU OK → TensorRT FAIL.

Nguyên nhân có thể: parser không hỗ trợ op/attribute combo; thiếu dynamic profile; dtype không phù hợp; graph chứa If/Loop; custom op chưa đăng ký; opset quá mới so với TRT version đang dùng.

Debug theo thứ tự:

  1. Confirm onnx.checker.check_model pass
  2. Confirm ORT CPU pass và numerical match với PyTorch
  3. Counter(n.op_type for n in model.graph.node) — list tất cả operators
  4. Tìm operator gần vị trí TRT báo lỗi
  5. Đối chiếu TRT support matrix cho version đang dùng
  6. Nếu dynamic shape: kiểm tra min/opt/max profile
  7. Nếu unsupported op: refactor model hoặc viết plugin

ONNX hợp lệ ≠ mọi backend chạy được. ONNX là chuẩn biểu diễn; backend vẫn có operator coverage riêng.

MẹoDebugging checklist (làm đúng thứ tự)
  1. onnx.load("model.onnx") — load thành công? Nếu fail: file hỏng, thiếu external data, version không tương thích
  2. onnx.checker.check_model(model) — schema hợp lệ?
  3. In opset_import — đối chiếu backend target version
  4. In input/output schema: name, dtype, shape
  5. Counter(n.op_type for n in model.graph.node) — list operators
  6. ort.InferenceSession("model.onnx", providers=["CPUExecutionProvider"]) — ORT CPU chạy?
  7. np.testing.assert_allclose(torch_out, ort_out, rtol=..., atol=...) — numerical match?
  8. Netron để nhìn graph nhanh (không thay code validation)

Nếu CPU fail: lỗi tại graph/input/export. Nếu CPU pass nhưng TRT fail: lỗi tại TRT operator coverage, dynamic profile, dtype, hoặc parser.

Lab 2A — Export static

Tạo lesson2_export_static.py:

import numpy as np
import onnx
import onnxruntime as ort
import torch
import torch.nn as nn
import torch.nn.functional as F


class TinyCNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv = nn.Conv2d(3, 8, kernel_size=3, padding=1)
        self.fc = nn.Linear(8 * 32 * 32, 10)

    def forward(self, x):
        x = self.conv(x)
        x = F.relu(x)
        x = torch.flatten(x, 1)
        return self.fc(x)


def main():
    torch.manual_seed(0)
    model = TinyCNN().eval()
    example_input = torch.randn(1, 3, 32, 32)

    # PyTorch 2.5+ recommended exporter path.
    onnx_program = torch.onnx.export(
        model,
        (example_input,),
        input_names=["images"],
        output_names=["logits"],
        opset_version=18,
        dynamo=True,
    )
    onnx_program.save("tinycnn_static.onnx")
    print("Saved tinycnn_static.onnx")

    # Validate ONNX structure.
    onnx_model = onnx.load("tinycnn_static.onnx")
    onnx.checker.check_model(onnx_model)
    print("ONNX checker passed")

    # Run ONNX Runtime and compare with PyTorch.
    session = ort.InferenceSession(
        "tinycnn_static.onnx", providers=["CPUExecutionProvider"]
    )
    ort_logits = session.run(["logits"], {"images": example_input.numpy()})[0]
    with torch.no_grad():
        torch_logits = model(example_input).numpy()
    np.testing.assert_allclose(torch_logits, ort_logits, rtol=1e-4, atol=1e-5)
    print("PyTorch and ONNX Runtime outputs match")
    print("Output shape:", ort_logits.shape)


if __name__ == "__main__":
    main()

Lab 2B — Inspect graph

Tạo lesson2_inspect_onnx.py:

import onnx


def describe_value_info(value_info):
    tensor_type = value_info.type.tensor_type
    dtype = onnx.TensorProto.DataType.Name(tensor_type.elem_type)
    dims = []
    for dim in tensor_type.shape.dim:
        if dim.HasField("dim_value"):
            dims.append(str(dim.dim_value))
        elif dim.HasField("dim_param"):
            dims.append(dim.dim_param)
        else:
            dims.append("?")
    return value_info.name, dtype, dims


def main():
    model = onnx.load("tinycnn_static.onnx")
    graph = model.graph

    print("IR version:", model.ir_version)
    print("Producer:", model.producer_name, model.producer_version)
    print("Opset imports:")
    for opset in model.opset_import:
        domain = opset.domain or "ai.onnx/default"
        print(f"  domain={domain}, version={opset.version}")

    print("\nGraph name:", graph.name)

    print("\nInputs:")
    for value in graph.input:
        name, dtype, dims = describe_value_info(value)
        print(f"  {name}: {dtype}[{', '.join(dims)}]")

    print("\nOutputs:")
    for value in graph.output:
        name, dtype, dims = describe_value_info(value)
        print(f"  {name}: {dtype}[{', '.join(dims)}]")

    print("\nInitializers / weights:")
    for tensor in graph.initializer:
        print(
            f"  {tensor.name}: "
            f"{onnx.TensorProto.DataType.Name(tensor.data_type)}{list(tensor.dims)}"
        )

    print("\nNodes:")
    for i, node in enumerate(graph.node):
        print(f"  [{i:02d}] {node.op_type}")
        print(f"       inputs : {list(node.input)}")
        print(f"       outputs: {list(node.output)}")
        if node.attribute:
            attrs = [attr.name for attr in node.attribute]
            print(f"       attrs  : {attrs}")


if __name__ == "__main__":
    main()

Lab 2C — Dynamic batch

Tạo lesson2_export_dynamic_batch.py:

import numpy as np
import onnx
import onnxruntime as ort
import torch
import torch.nn as nn
import torch.nn.functional as F


class TinyCNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv = nn.Conv2d(3, 8, kernel_size=3, padding=1)
        self.fc = nn.Linear(8 * 32 * 32, 10)

    def forward(self, x):
        x = F.relu(self.conv(x))
        x = torch.flatten(x, 1)
        return self.fc(x)


def main():
    torch.manual_seed(0)
    model = TinyCNN().eval()
    example_input = torch.randn(2, 3, 32, 32)
    # Key "x" = tên argument trong forward(self, x),
    # không phải ONNX input name "images".
    batch_dim = torch.export.Dim("batch", min=1, max=64)

    onnx_program = torch.onnx.export(
        model,
        (example_input,),
        input_names=["images"],
        output_names=["logits"],
        dynamic_shapes={"x": {0: batch_dim}},
        opset_version=18,
        dynamo=True,
    )
    onnx_program.save("tinycnn_dynamic_batch.onnx")
    print("Saved tinycnn_dynamic_batch.onnx")

    onnx.checker.check_model(onnx.load("tinycnn_dynamic_batch.onnx"))
    print("ONNX checker passed")

    session = ort.InferenceSession(
        "tinycnn_dynamic_batch.onnx", providers=["CPUExecutionProvider"]
    )
    for batch_size in [1, 4, 8]:
        x = torch.randn(batch_size, 3, 32, 32)
        ort_logits = session.run(["logits"], {"images": x.numpy()})[0]
        with torch.no_grad():
            torch_logits = model(x).numpy()
        np.testing.assert_allclose(torch_logits, ort_logits, rtol=1e-4, atol=1e-5)
        print(f"batch={batch_size}: OK {ort_logits.shape}")


if __name__ == "__main__":
    main()

Glossary

Thuật ngữ Giải thích ngắn
ONNX Open format/spec biểu diễn ML model
ONNX Runtime Runtime chạy ONNX trên CPU/GPU/accelerators
TensorRT Compiler/runtime tối ưu inference NVIDIA GPU
Graph Dataflow gồm node và tensor edges
Node Một lần gọi operator trong graph
Operator Định nghĩa phép toán (Conv, Relu, …)
Opset Versioned set of operator specifications
IR version Version của ONNX IR format
Initializer Tensor constant trong graph, thường weights
ValueInfo Metadata name/dtype/shape của tensor
Dynamic shape Có dimension symbolic/runtime-dependent
Static shape Mọi dimension cố định
Execution Provider Backend thực thi trong ORT
Shape inference Suy luận shape intermediate tensors
Graph optimization Rewrite graph giữ semantics (folding, fusion, …)
Attribute Cấu hình tĩnh của operator (strides, pads, …)
NCHW / NHWC Layout tensor ảnh: channel trước/sau spatial dims

Summary

  1. ONNX là IR, không phải runtime.
  2. Model = graph + weights + I/O schema + metadata + opset.
  3. Node = lần dùng operator; initializer = weights đã lưu sẵn, không phải runtime input.
  4. Chọn opset theo backend; đừng nhầm IR version / opset version / model version.
  5. Export = capture graph, không chỉ save weights; luôn model.eval() + validate số học.
  6. Dynamic shape có chủ đích; layout/dtype sai có thể không crash nhưng output sai im lặng.
  7. ORT chạy được ≠ TensorRT build được — mỗi backend có operator coverage riêng.
