Bối cảnh

Bạn đang học ONNX và TensorRT. Hai công nghệ này thường được giới thiệu bằng những câu như:

  • Export model từ PyTorch sang ONNX
  • Build TensorRT engine
  • Chạy inference nhanh hơn
  • Deploy bằng Triton

Cách học đó có thể giúp bạn chạy được demo, nhưng thường không giúp bạn debug khi gặp lỗi thực tế như:

  • ONNX export sai shape
  • TensorRT không hỗ trợ một operator
  • Dynamic shape làm engine build fail
  • INT8 quantization (giảm precision) làm accuracy giảm
  • GPU utilization cao nhưng latency p99 vẫn tệ
  • Triton dynamic batching tăng throughput nhưng làm tail latency vượt SLO

Vì vậy, bài đầu tiên tập trung vào kiến trúc inference hiện đại. Sau bài này, ONNX và TensorRT không còn là các tool rời rạc, mà trở thành các mảnh ghép rõ ràng trong một pipeline production.

Prerequisites

1.1 Big picture: từ training tới serving

Vì sao một model đã đạt accuracy tốt trên tập test vẫn có thể làm service chậm khi lên production?

Quan trọngÝ chính

Training tối ưu cho tổng thời gian xử lý toàn bộ dataset. Inference production tối ưu cho thời gian phản hồi của từng request. Hai mục tiêu này dẫn tới hai thiết kế hệ thống khác nhau.

Một pipeline machine learning production thường có hai thế giới:

Training thường tối ưu cho throughput dài hạn: nhiều data, nhiều epoch, nhiều GPU, nhiều giờ hoặc ngày.

Inference production tối ưu cho request-level behavior. Mỗi request phải được phản hồi trong khoảng thời gian chấp nhận được. Service thường đặt SLO (Service Level Objective) như:

  • p99 latency < 100 ms
  • availability ≥ 99.9%
  • throughput ≥ 1000 requests/second

Một model train tốt chưa chắc phục vụ tốt. Production inference cần thêm tối ưu, scheduling, batching, memory management, monitoring và rollout.

MẹoCon số cụ thể

Một service phân loại ảnh có GPU execution chỉ 8 ms, nhưng end-to-end là 51 ms. Model chiếm khoảng 15% thời gian người dùng thực sự chờ. Chi tiết ở Mục 1.8.

1.2 Model artifact khác gì inference service?

Model file sau training trả lời câu hỏi gì — và inference service trả lời câu hỏi gì khác?

Quan trọngÝ chính

Model artifact lưu graph/weights đã học. Inference service nhận request, xử lý ổn định, đạt latency/throughput mục tiêu, quan sát lỗi và rollout an toàn. Artifact chưa phải service.

1.2.1 Model artifact

Model artifact là sản phẩm của quá trình training. Nó có thể là file weight, checkpoint, serialized model, TorchScript module, ONNX model, hoặc TensorRT engine.

Artifact trả lời: Model đã học được gì, và computation graph hoặc weights được lưu ở đâu?

1.2.2 Inference service

Inference service trả lời: Làm sao nhận request từ user, xử lý input, chạy model ổn định, trả output đúng format, đạt latency/throughput mục tiêu, quan sát được lỗi, và rollout an toàn?

Một inference service thường bao gồm:

Thành phần Vai trò
API layer Nhận request qua HTTP/gRPC/message queue
Input validation Kiểm tra schema, size, dtype, range, authentication
Preprocessing Decode ảnh, tokenize text, resize, normalize, pad/truncate
Scheduler Queue request, gom batch, điều phối worker/GPU
Runtime ONNX Runtime, TensorRT, PyTorch eager, TensorFlow Serving, vLLM, v.v.
GPU execution Kernel launch, memory transfer, compute, synchronization
Postprocessing Softmax, NMS, decode token, map label, format result
Observability Metrics, logs, traces, profiling, alerting
Deployment control Versioning, rollback, canary, A/B testing

Sai lầm phổ biến là chỉ nhìn Input → Model → Output. Trong production, dòng đúng hơn là request đi qua queue, preprocess, transfer, execute, postprocess rồi mới response. Nếu chỉ tối ưu bước execute mà bottleneck thật nằm ở queue hoặc preprocess, service vẫn chậm.

Cảnh báoBẫy thường gặp

Chỉ tối ưu bước execute — thực tế bottleneck có thể nằm ở queue hoặc preprocess. Service vẫn chậm dù model đã nhanh.

MẹoĐào sâu: chi phí ẩn quanh model

Ngoài thời gian chạy model, end-to-end còn gồm: queue latency (request chờ đến lượt), CPU↔︎GPU transfer (H2D/D2H), batching delay (chờ gom đủ batch), serialization (đóng gói kết quả) và postprocessing logic (softmax, NMS, decode). User cảm nhận tổng của tất cả các phần này — không chỉ phần GPU.

1.3 Anatomy of one inference request

Khi user gửi một request, thời gian thực sự đi vào những đoạn nào trước khi có response?

Quan trọngÝ chính

Trong demo bạn thường đo L_gpu_execute. Trong production, user cảm nhận L_total. Nếu preprocess chiếm phần lớn budget, tăng tốc model gần như không cứu được SLO.

Sơ đồ xương sống của bài này — pipeline một request:

Latency (thời gian xử lý một request) end-to-end là tổng các giai đoạn: network, queue, preprocess, H2D (host-to-device), GPU execute, D2H (device-to-host), postprocess, serialize.

1.3.1 Latency budget

Giả sử SLO là p99 latency < 100 ms. Một budget ban đầu:

Thành phần Budget
Network + API parsing 5 ms
Queueing 10 ms
Preprocessing 15 ms
H2D transfer 5 ms
GPU execution 40 ms
D2H transfer 5 ms
Postprocessing + serialization 10 ms
Safety margin 10 ms
Total 100 ms

Nếu preprocessing thực tế là 45 ms, TensorRT giảm GPU execution từ 40 ms xuống 20 ms thì tổng vẫn có thể vượt SLO. Inference optimization cần nhìn cả hệ thống, không chỉ nhìn model.

MẹoCon số cụ thể: model nhanh 2.67× nhưng service chỉ cải thiện 9.8%

Service image classification có breakdown latency đo được:

Thành phần Trước TensorRT Sau TensorRT
API parse 2 ms 2 ms
Image decode + resize 35 ms 35 ms
H2D copy 3 ms 3 ms
GPU execution 8 ms 3 ms
D2H copy 1 ms 1 ms
Postprocessing 2 ms 2 ms
Total 51 ms 46 ms

Tính cụ thể: 2 + 35 + 3 + 3 + 1 + 2 = 46 ms. TensorRT đã tăng tốc GPU execution 2.67× (từ 8 ms xuống 3 ms), nhưng end-to-end chỉ cải thiện 9.8% (từ 51 ms xuống 46 ms).

Kết luận: bottleneck thật là image decode + resize (35 ms), không phải GPU execution. Tiếp tục tối ưu model sẽ không mang lại nhiều. Cần song song hoá preprocessing, dùng thư viện decode nhanh hơn (libjpeg-turbo, DALI), hoặc đẩy preprocessing lên GPU.

1.4 GPU mental model

GPU có phải là CPU nhanh hơn — và inference trên GPU thực chất là chuỗi thao tác gì?

Quan trọngÝ chính

GPU là throughput machine: rất nhiều worker đơn giản chạy song song. Deep learning inference là chuỗi kernel launches và memory operations trên device, không phải một phép tính kỳ diệu duy nhất.

1.4.1 GPU không phải CPU nhanh hơn

CPU và GPU được thiết kế cho hai kiểu workload khác nhau:

CPU GPU
Thiết kế cho Ít worker linh hoạt, logic phức tạp Rất nhiều worker, công việc chia đều
Mạnh ở Branching, control flow, task nhỏ latency thấp Data parallelism, matmul, tensor ops, bandwidth lớn
Phù hợp OS, networking, orchestration Convolution, attention, elementwise song song

Deep learning inference chủ yếu là phép toán tensor — convolution, matrix multiplication, attention, normalization, elementwise — có tính song song rất cao, nên phù hợp GPU.

Một mental model đơn giản: CPU là ít worker rất linh hoạt và mạnh với logic phức tạp; GPU là rất nhiều worker đơn giản hơn, nhưng tổng throughput rất lớn nếu công việc được chia đều.

1.4.2 Host, device và transfer

Trong CUDA-style programming:

  • Host = CPU + system RAM
  • Device = GPU + GPU memory / VRAM

Request thường được nhận và preprocess trên host. Tensor input cần nằm ở device memory để GPU tính. Output có thể được copy về host để postprocess. Nguồn latency hay bị bỏ qua là transfer CPU RAM ↔︎ GPU VRAM: tensor nhỏ thì overhead transfer và kernel launch chiếm tỷ lệ lớn; tensor lớn thì bandwidth host–device có thể trở thành bottleneck.

1.4.3 Kernel, SM, warp

CUDA kernel là function chạy song song trên GPU. Khi runtime chạy convolution, matmul hoặc activation, nó thường gọi một hoặc nhiều kernel đã tối ưu từ thư viện cuDNN, cuBLAS hoặc kernel custom.

Một GPU NVIDIA gồm nhiều SM (Streaming Multiprocessor) — đơn vị thực thi chính. CUDA chia công việc thành thread; thread được nhóm thành block; GPU schedule các block lên SM. Ở mức thực thi phần cứng, thread chạy theo nhóm gọi là warp — thường là 32 thread cùng lúc theo mô hình SIMT (Single Instruction, Multiple Threads).

Bạn chưa cần viết CUDA kernel. Nhưng bạn cần hiểu: một model inference thực chất là chuỗi kernel launches và memory operations. Hiểu mô hình này giúp đọc các khái niệm occupancy, memory bandwidth, kernel fusion và launch overhead.

MẹoĐào sâu: SM, warp và occupancy

Mỗi SM có một số lượng hữu hạn register, shared memory và warp slot. Occupancy là tỷ lệ warp đang active trên SM so với tối đa có thể. Occupancy cao không luôn đồng nghĩa performance tốt — đôi khi một kernel tận dụng tốt shared memory và compute ngay cả khi occupancy thấp.

Với deep learning inference dùng TensorRT hoặc ONNX Runtime, runtime và thư viện kernel sẽ điều phối thread/block. Bạn không trực tiếp viết scheduling. Tuy nhiên, hiểu mô hình này giúp đọc profiler (như Nsight Systems/Compute) khi cần chẩn đoán tại sao một kernel chạy chậm hơn kỳ vọng.

1.4.4 Memory hierarchy

Bộ nhớ Đặc điểm Ghi chú
Registers Rất nhanh, rất nhỏ Riêng cho thread
Shared memory Nhanh, nhỏ Chia sẻ trong một block
L1/L2 cache Trung gian Giảm global memory access
Global memory / VRAM Lớn, chậm hơn register/shared Tensors, weights, activations
Host memory RAM phía CPU Cần transfer nếu GPU cần dữ liệu

Nhiều model không bị giới hạn bởi số phép tính mà bởi tốc độ đọc/ghi bộ nhớ — gọi là memory-bound. Ngược lại, model bị giới hạn bởi số phép tính gọi là compute-bound.

Ví dụ thực tế:

  • Large matrix multiplication thường có thể tận dụng compute tốt (compute-bound).
  • Chuỗi elementwise operations nhỏ bị chi phối bởi memory bandwidth và kernel launch overhead (memory-bound).
  • Attention decode trong LLM thường bị ảnh hưởng nặng bởi memory access tới KV cache (memory-bound).

1.4.5 Tensor Cores

Tensor Cores là phần cứng chuyên dụng trong GPU NVIDIA để tăng tốc các phép matrix/tensor math ở một số precision nhất định. Tùy kiến trúc GPU: FP16, BF16, TF32, INT8, FP8.

Vì deep learning dùng rất nhiều matmul và convolution, Tensor Cores là lý do các precision thấp như FP16, BF16, INT8 có thể tăng tốc mạnh. Nhưng đổi precision không chỉ là bật một flag. Cần kiểm tra:

  • Hardware có hỗ trợ precision đó không
  • Runtime có kernel tối ưu cho operator đó không
  • Accuracy có bị giảm không
  • Shape có phù hợp để kernel chạy hiệu quả không (ví dụ: alignment 8 hoặc 16 thường cần thiết)

1.4.6 CUDA streams và concurrency

CUDA stream là hàng đợi công việc trên GPU. Operation trong cùng một stream thường giữ thứ tự. Các stream khác nhau có thể cho phép overlap một số công việc, tùy hardware, runtime và dependency.

Stream A: H2D copy req 1 → execute req 1 → D2H copy req 1
Stream B: H2D copy req 2 → execute req 2 → D2H copy req 2

Nếu thiết kế tốt, service có thể overlap data transfer, compute và nhiều request. Tuy nhiên, concurrency không tự động tạo performance tốt. Quá nhiều concurrency có thể làm queue dài, tăng memory pressure và làm p99 xấu đi.

MẹoĐào sâu: GPU nằm đâu trên pipeline xương sống?

Trên sơ đồ ở Hình 1.2, giai đoạn GPU là nơi kernel, SM, warp và Tensor Cores hoạt động. Giai đoạn H2D và D2H hai bên là transfer host↔︎device — thường bị bỏ quên khi chỉ đo model latency bằng cách đặt timer bao quanh session.run(). Để đo đúng H2D/D2H, cần profiler như Nsight Systems.

1.5 Inference stack: ONNX, Runtime, TensorRT, Triton

ONNX, ONNX Runtime, TensorRT và Triton khác nhau thế nào — và vì sao không thể thay thế lẫn nhau?

Quan trọngÝ chính

ONNX là representation. ONNX Runtime là runtime đa backend. TensorRT là compiler + runtime tối ưu sâu cho GPU NVIDIA. Triton là serving server. Nhầm vai trò là nguyên nhân phổ biến của thiết kế stack sai.

Một neural network là computation graph: mỗi node là operation, mỗi edge là tensor. Khi train bằng PyTorch bạn thường làm việc với Python objects và dynamic execution. Khi deploy, runtime muốn graph rõ ràng hơn để tối ưu — đây là nơi ONNX, ONNX Runtime và TensorRT xuất hiện.

Ví dụ đồ thị khái niệm: Input → Conv → BatchNorm → ReLU → MaxPool → Linear → Softmax → Output. Mỗi node là operation, mỗi edge là tensor flow giữa các operation.

1.5.1 Vai trò từng lớp

Công nghệ Vai trò chính Không nên hiểu nhầm là
ONNX Model representation / interchange format Một serving server
ONNX Runtime Runtime chạy ONNX trên nhiều backend Chỉ dành cho CPU
TensorRT NVIDIA inference compiler + runtime Chỉ là Python wrapper
Triton Inference serving server Một model optimizer
CUDA Programming/runtime layer cho NVIDIA GPU Một deep learning framework

ONNX định nghĩa file format và tập operator chung để model đi qua nhiều framework, runtime và hardware backend. Nó trả lời: graph gồm những node, tensor, operator, shape, dtype nào — không phải GPU runtime.

ONNX Runtime chạy ONNX model, áp dụng graph optimizations và dùng Execution Providers (CPU, CUDA, TensorRT, OpenVINO, CoreML, DirectML, QNN, …).

TensorRT nhận model (thường qua ONNX) và tạo optimized engine cho GPU NVIDIA. Không chỉ là runtime — TensorRT có phần compiler/optimizer rất quan trọng.

Triton không thay thế ONNX hay TensorRT. Nó phụ trách model repository, multi-model serving, dynamic batching, concurrent execution, versioning, metrics, HTTP/gRPC và backend integration.

1.5.2 Putting the stack together

Không có stack duy nhất đúng. Tùy use case:

Stack Khi nào dùng
PyTorch → ONNX → TensorRT → Triton Production NVIDIA GPU, cần throughput tối đa
PyTorch → ONNX → ORT (CUDA EP) → FastAPI Cần flexibility, không muốn TRT build time
PyTorch → Torch-TensorRT → TensorRT → Triton Tránh ONNX export, tích hợp trực tiếp TRT vào PyTorch
PyTorch eager → Triton Python backend Prototype nhanh, chưa cần tối ưu sâu

Điều quan trọng là hiểu vai trò từng lớp, không bắt buộc một stack cố định. Ví dụ, ONNX Runtime với CUDA Execution Provider đủ dùng cho nhiều service không cần tối ưu cực đại của TensorRT.

1.5.3 Vì sao TensorRT tồn tại?

Framework training như PyTorch rất linh hoạt, nhưng linh hoạt không luôn tối ưu nhất cho inference production. TensorRT biến model đã train thành execution plan tối ưu hơn cho GPU NVIDIA qua các bước:

Khả năng Ý nghĩa thực tế
Graph cleanup Bỏ node dư thừa; đơn giản hóa pattern
Layer fusion Gộp nhiều layer để giảm memory access và kernel launch
Precision optimization FP16/BF16/INT8/FP8: giảm bandwidth, tăng tốc Tensor Cores
Tactic selection Chọn kernel/thuật toán tốt nhất theo GPU, shape, precision
Memory planning Lập kế hoạch buffer intermediate, tái sử dụng memory
Dynamic shape profiles Tối ưu cho range shape thay vì một shape cố định
Engine serialization Lưu engine để tái sử dụng, tránh build lại
MẹoĐào sâu: từng loại tối ưu của TensorRT

Graph cleanup và constant folding

Một graph có thể có node dư thừa từ quá trình export:

Trước: x → Identity → y
Sau:   x → y

Hoặc một số phép tính chỉ dùng constant có thể được tính trước (constant folding), giảm compute lúc inference.

Layer fusion

Nhiều layer liên tiếp được fuse để giảm số kernel launches và số lần đọc/ghi global memory. Ví dụ:

Conv → BatchNorm → ReLU

Có thể được thực thi hiệu quả hơn dưới dạng một fused operation. Tương tự:

MatMul → Add (bias) → Activation

Thay vì ba kernel riêng, TensorRT có thể map sang một kernel/tactic tối ưu hơn.

Precision optimization

Thay vì FP32 mọi nơi, inference có thể dùng precision thấp hơn. Lợi ích: giảm memory bandwidth, giảm footprint, tăng tốc Tensor Cores. Rủi ro: accuracy giảm, operator không hỗ trợ, calibration không tốt.

Tactic selection

Với cùng operation như convolution hay matmul, có nhiều thuật toán/kernel. TensorRT có thể benchmark hoặc chọn tactic phù hợp với GPU architecture, tensor shape, precision, workspace memory limit và dynamic shape profile. Đây là lý do engine có thể phụ thuộc vào hardware, shape range và config build.

Memory planning

TensorRT lập kế hoạch memory cho intermediate tensors: giảm allocation runtime, tái sử dụng buffer hiệu quả. Quan trọng khi GPU memory hữu hạn, multi-model serving cần chia sẻ GPU, hoặc batch size lớn làm activation memory tăng.

Engine tối ưu trên GPU này chưa chắc tối ưu trên GPU khác — đây là lý do thường phải build engine trên cùng hardware sẽ chạy inference.

1.6 Latency, throughput và trade-off batching

Vì sao tăng throughput bằng batching lại có thể làm p99 latency xấu đi?

Quan trọngÝ chính

Production quan tâm p99 hơn average. Batching tăng throughput nhưng thêm queue delay — luôn tune theo SLO, không theo “GPU bận hơn”.

1.6.1 Latency, throughput, utilization, concurrency

Latency là thời gian từ request sent tới response received.

Metric Ý nghĩa
Average latency Trung bình, dễ bị che bởi outlier
Median / p50 50% request nhanh hơn giá trị này
p95 95% request nhanh hơn giá trị này
p99 99% request nhanh hơn giá trị này
Max Request chậm nhất quan sát được

Production thường quan tâm p95 hoặc p99 vì một phần nhỏ request chậm có thể phá trải nghiệm hoặc làm downstream system timeout.

Throughput là số request xử lý được mỗi đơn vị thời gian:

\[\text{throughput} = \frac{\text{completed requests}}{\text{second}}\]

Đơn vị thường gặp: RPS, QPS, images/sec, tokens/sec (LLM).

GPU utilization cao không luôn nghĩa service tốt: GPU có thể bận vì queue dài, p99 xấu, kernel kém hiệu quả, hoặc memory-bound. Utilization thấp cũng không luôn là lỗi: batch size = 1 với SLO latency rất chặt, traffic thưa, hoặc bottleneck nằm ở CPU/network.

Concurrency là số request đang trong hệ thống cùng lúc. Rule-of-thumb từ queueing theory:

\[\text{concurrency} \approx \text{throughput} \times \text{latency}\]

Ví dụ: 500 RPS × 100 ms = khoảng 50 request đồng thời. Đây chỉ là trực giác ban đầu; với p99, burst traffic, batching và queueing, behavior phức tạp hơn nhiều.

1.6.2 Latency–throughput trade-off

Batch size = 1 Batch size lớn
Ưu Không chờ gom batch; latency đơn request thường thấp; dễ reasoning Tăng arithmetic intensity; tận dụng GPU tốt; throughput cao
Nhược GPU có thể under-utilized; launch overhead lớn; matmul nhỏ kém hiệu quả Phải chờ batch/timeout; memory tăng; p99 có thể xấu

Dynamic batching là kỹ thuật server chờ một khoảng rất ngắn để gom nhiều request độc lập thành một batch:

0.0 ms: request A arrives
0.7 ms: request B arrives
1.2 ms: request C arrives
1.5 ms: dispatch batch [A, B, C]

Nếu batch size 3 hiệu quả hơn nhiều so với ba lần batch size 1, throughput tăng. Nếu chờ quá lâu, latency tăng. Cấu hình thường gồm: max batch size, max queue delay, preferred batch sizes, number of instances, SLO target. Chi tiết khi tới Triton.

MẹoCon số cụ thể: batching tăng throughput 2.6× nhưng p99 vượt SLO

Example 2 — batch throughput vs p99 SLO

Service object detection có traffic không đều. Bạn bật dynamic batching với max queue delay = 20 ms.

Metric Trước batching Sau batching
Throughput 200 RPS 520 RPS
Average latency 30 ms 42 ms
p99 latency 70 ms 145 ms

Throughput tăng 2.6× — nhưng nếu SLO là p99 < 100 ms, cấu hình này không đạt dù throughput tăng mạnh. Lý do: với max queue delay = 20 ms, một request có thể chờ gần 20 ms chỉ để vào batch, chưa tính model execution và các giai đoạn khác. Tail latency tăng vọt.

Hướng xử lý:

  • Giảm max queue delay (ví dụ xuống 5 ms) để giảm queueing tail
  • Chọn preferred batch size nhỏ hơn (ví dụ 4 thay vì 8)
  • Tăng number of instances để xử lý song song nhiều batch hơn
  • Tách traffic theo priority: request latency-sensitive xử lý riêng
  • Autoscale nhiều replicas hơn khi traffic tăng
MẹoCon số cụ thể: GPU utilization thấp không nhất thiết là xấu

Example 3 — low GPU utilization với SLO rất chặt

Một real-time fraud detection service yêu cầu p99 < 20 ms. Model nhỏ, batch size = 1. GPU utilization chỉ 25%.

Đây có thể chấp nhận được nếu:

  • Latency đạt SLO (p99 < 20 ms đạt được)
  • Cost chấp nhận được
  • Traffic không đủ lớn để batch có lợi
  • Business ưu tiên phản hồi nhanh hơn throughput

Tối ưu utilization lên 90% bằng cách bật dynamic batching max delay = 50 ms sẽ làm p99 thành 80 ms — vượt SLO 4×. Đó là thất bại dù nhìn “hiệu quả hơn” trên dashboard.

Bài học: GPU utilization là phương tiện, không phải mục tiêu. Mục tiêu là đạt SLO với cost hợp lý.

1.7 Bottleneck và workflow tối ưu

Bước đầu tiên khi tối ưu inference là gì — dùng TensorRT, hay hỏi bottleneck nằm ở đâu?

Quan trọngÝ chính

Đừng bắt đầu bằng “làm sao dùng TensorRT?”. Hãy bắt đầu bằng “bottleneck hiện tại là gì?”. Đo baseline end-to-end trước, rồi mới chọn tool.

1.7.1 Các loại bottleneck phổ biến

Loại bottleneck Dấu hiệu nhận biết Cần đo gì Hướng xử lý
Compute-bound GPU compute cao, Tensor Cores bận, tăng batch thì throughput tăng GPU SM active %, Tensor Core utilization FP16/BF16/INT8, TensorRT, kernel fusion, shape alignment, đổi architecture
Memory-bound Bandwidth cao nhưng compute thấp; nhiều elementwise / attention decode GPU memory bandwidth util Kernel fusion, layout tối ưu, quantization, KV cache
Transfer-bound H2D/D2H đáng kể; model nhanh nhưng e2e vẫn chậm H2D/D2H duration trong profiler Giảm số lần copy, pinned memory, overlap bằng stream, giữ postprocess trên GPU
Preprocess-bound CPU cao, GPU idle; decode/tokenize tốn thời gian CPU utilization per core, preprocessing p99 Song song hoá, đẩy lên GPU, cache, đổi thư viện, giảm serialization
Queue-bound Latency tăng vọt khi traffic tăng; p99 xấu; queue dài Queue length, queueing latency p99 Chỉnh batching delay, thêm instance, autoscale, admission control, backpressure

1.7.2 Workflow chuẩn

  1. Define target — p99 latency, throughput, cost/request, GPU type, accuracy constraint
  2. Measure baseline — end-to-end, model-only, preprocess, queueing, GPU/CPU util, memory
  3. Identify bottleneck — compute / memory / transfer / preprocess / queueing
  4. Apply targeted optimization — TensorRT, quantization, batching, preprocess, replicas
  5. Validate — accuracy, p50/p95/p99, throughput under load, stability, memory footprint
  6. Roll out safely — canary, A/B, shadow traffic, rollback plan
Cảnh báoBẫy thường gặp

Bỏ qua baseline rồi tối ưu bằng cảm giác hoặc vì tool nghe mạnh — dễ tối ưu nhầm chỗ. TensorRT không giải quyết bottleneck ở tokenization, image decode, network hay queueing.

1.8 Worked examples

Nhìn vào số đo, làm sao biết mình đang tối ưu đúng chỗ — trước khi mở terminal hay benchmark?

Quan trọngÝ chính

Ba ví dụ dưới đây minh hoạ ba bẫy phổ biến: tối ưu nhầm chỗ, bật batching không đúng cấu hình, và nhầm GPU utilization thấp là vấn đề. Tất cả đều có nguyên nhân là không đo đúng trước khi quyết định.

Example 1: model nhanh nhưng service chậm

Service image classification đo được:

Thành phần Latency

Image decode + resize 35 ms

GPU execution 8 ms
D2H copy 1 ms
Postprocessing 2 ms
Total 51 ms

Bạn dùng TensorRT và giảm GPU execution từ 8 ms xuống 3 ms. Latency mới: 2 + 35 + 3 + 3 + 1 + 2 = 46 ms.

Bạn đã tăng tốc model 2.67×, nhưng end-to-end latency chỉ cải thiện từ 51 ms xuống 46 ms — tức khoảng 9.8%.

Kết luận: bottleneck thật là image decode + resize (35 ms), không phải GPU execution. Tiếp tục tối ưu model sẽ không mang lại nhiều. Bước tiếp theo đúng là: profile preprocessing, thử libjpeg-turbo thay libjpeg chuẩn, hoặc đẩy resize lên GPU với DALI.

Example 2: batch size tăng throughput nhưng làm p99 xấu

Service object detection có traffic không đều. Bạn bật dynamic batching với max queue delay = 20 ms.

Metric Trước batching Sau batching
Throughput 200 RPS 520 RPS

p99 latency 70 ms 145 ms

Nếu SLO là p99 < 100 ms, cấu hình batching này không đạt dù throughput tăng 2.6×. Với max queue delay = 20 ms, request đến lúc queue vắng vẫn phải chờ gần 20 ms trước khi vào batch — chưa tính model execution và các giai đoạn khác. Tail latency vọt lên 145 ms.

Example 3: GPU utilization thấp không nhất thiết là xấu

Real-time fraud detection yêu cầu p99 < 20 ms. Model nhỏ, batch size = 1 vì mỗi transaction cần phản hồi ngay. GPU utilization chỉ 25%.

Điều này hoàn toàn chấp nhận được nếu:

  • p99 latency đạt SLO (< 20 ms)
  • Cost hợp lý với business
  • Traffic không đủ lớn để batch có lợi
  • Business ưu tiên phản hồi nhanh hơn throughput tối đa

Nếu bạn tối ưu utilization lên 90% bằng cách bật batching với max delay = 50 ms, p99 có thể tăng lên 80 ms — vượt SLO 4×. Đó là thất bại dù dashboard GPU trông “hiệu quả hơn”.

Bài học: GPU utilization là phương tiện đo lường, không phải mục tiêu. Tối ưu theo SLO, không theo utilization.

MẹoTám nguyên tắc thiết kế cho inference engineer

1. Measure end-to-end, then measure model-only

Luôn tách: end-to-end latency, model execution latency, queue latency, preprocess/postprocess latency, transfer latency. Nếu không tách, bạn không biết tối ưu ở đâu. Ba ví dụ trên đều có thể tránh được nếu đo đúng từ đầu.

2. p99 quan trọng hơn average trong production

Average latency có thể đẹp nhưng p99 xấu. User và downstream system thường bị ảnh hưởng bởi tail latency — một request retry từ downstream do timeout có thể gây cascade failure. Monitor p95 và p99, đặt SLO theo p99.

3. Batching là con dao hai lưỡi

Batching có thể tăng throughput, nhưng có thể làm latency tăng — đặc biệt là tail latency. Luôn tune batching theo SLO: thử nhiều max queue delay, đo p99 thực tế dưới load thực. Đừng chỉ đo average.

4. Precision thấp cần validation

FP16/BF16/INT8/FP8 có thể nhanh hơn nhưng cần kiểm tra accuracy và numerical stability. Một số operator có thể không hỗ trợ precision mong muốn, hoặc cần calibration cẩn thận cho INT8. Luôn chạy accuracy check trên representative dataset trước khi deploy precision thấp.

5. Runtime optimization không thay thế model design

Một model quá lớn, shape không phù hợp, hoặc architecture kém inference-friendly (ví dụ: nhiều dynamic control flow, operator không hỗ trợ) vẫn khó tối ưu dù dùng TensorRT. Model architecture phải được thiết kế với inference efficiency trong đầu từ đầu.

6. Optimize bottleneck, not the tool you like

TensorRT rất mạnh, nhưng nếu bottleneck nằm ở tokenization hoặc image decode, TensorRT không giải quyết gốc vấn đề. Chọn tool dựa trên kết quả đo, không dựa trên xu hướng hoặc quen thuộc.

7. Hardware matters

Engine, precision và tactic có thể phụ thuộc vào GPU architecture. TensorRT engine build trên A100 không nhất thiết tối ưu trên T4 hay H100. Luôn build và benchmark engine trên hardware mà service sẽ chạy thực tế.

8. Production inference cần rollout strategy

Mọi optimization đều có rủi ro: accuracy regression, memory spike, cold-start latency spike, behavior thay đổi khi load cao. Cần canary, rollback và monitoring trước khi đưa ra toàn bộ traffic.

Checkpoint questions

MẹoTự kiểm (mở từng câu khi cần)

  1. Vì sao trained model artifact chưa phải production service?
    Vì artifact chỉ lưu graph/weights hoặc model representation. Production service còn cần API, validation, preprocessing, scheduling, batching, runtime execution, postprocessing, monitoring, scaling, versioning và rollout. Artifact trả lời “model đã học gì”, service trả lời “làm sao phục vụ ổn định”.

  2. ONNX có phải là runtime không?
    Không. ONNX chủ yếu là format/representation cho model. Runtime như ONNX Runtime hoặc TensorRT mới là thứ thực thi model.

  3. ONNX Runtime khác TensorRT thế nào?
    ONNX Runtime là runtime đa backend cho ONNX model, có thể chạy qua nhiều Execution Providers như CPU, CUDA, TensorRT, OpenVINO. TensorRT là NVIDIA inference compiler/runtime tối ưu sâu cho GPU NVIDIA, có phần compiler quan trọng riêng.

  4. TensorRT engine là gì?
    Execution plan đã optimize/compile cho một model, một tập shape/profile, precision config và hardware target nhất định. Không phải “file model nhanh hơn một chút” — nó là kết quả của quá trình compile/tactic selection.

  5. Vì sao batch size lớn có thể tăng throughput?
    Batch size lớn giúp GPU có nhiều công việc song song, matrix operations lớn hơn, giảm tỷ lệ kernel launch overhead trên mỗi sample. Nhưng memory và queueing latency có thể tăng, làm p99 xấu.

  6. Vì sao p99 latency quan trọng?
    p99 phản ánh tail behavior. Average đẹp vẫn có thể gây timeout hoặc trải nghiệm xấu nếu 1% request chậm bất thường. Downstream service thường timeout dựa trên tail, không dựa trên average.

  7. GPU utilization thấp có luôn là vấn đề không?
    Không. Nếu đạt latency SLO, traffic thấp, workload nhỏ hoặc business ưu tiên phản hồi nhanh, utilization thấp có thể chấp nhận được. Ví dụ fraud detection với batch size = 1 và p99 < 20 ms.

  8. Kernel fusion giúp gì?
    Giảm số kernel launches và giảm đọc/ghi intermediate tensors vào global memory. Điều này cải thiện latency và memory bandwidth efficiency, đặc biệt với chuỗi elementwise operations.

  9. Khi nào TensorRT không giải quyết được bottleneck?
    Khi bottleneck nằm ngoài model execution: preprocessing, network latency, queueing, serialization, H2D/D2H transfer, hoặc CPU tokenization. TensorRT chỉ tối ưu giai đoạn GPU execution.

  10. Bước đầu tiên khi tối ưu inference là gì?
    Xác định target (p99, throughput, accuracy constraint) và đo baseline end-to-end. Không nên tối ưu bằng cảm giác hoặc chỉ vì một tool nghe có vẻ mạnh.

Summary

  1. Inference production không chỉ là model(input).
  2. Latency end-to-end gồm queueing, preprocessing, H2D transfer, GPU execution, D2H transfer, postprocessing — user cảm nhận tổng, không chỉ phần GPU.
  3. GPU là throughput machine, không phải CPU nhanh hơn. Phù hợp với data-parallel tensor ops, không phải branching phức tạp.
  4. Deep learning inference là chuỗi kernel launches và memory operations trên SM qua warp, tận dụng Tensor Cores khi dùng precision thấp.
  5. ONNX là representation; ONNX Runtime là runtime đa backend; TensorRT là NVIDIA compiler/runtime tối ưu sâu (graph cleanup, fusion, precision, tactic selection, memory planning); Triton là serving server.
  6. Batching tăng throughput nhưng có thể làm p99 xấu — luôn tune theo SLO.
  7. Tối ưu inference: đo baseline end-to-end → tìm bottleneck đúng loại → tối ưu đúng chỗ → validate accuracy + p99 → rollout an toàn.

Nếu bạn nắm chắc bài này, các bài sau về ONNX graph, Execution Providers, TensorRT engine, quantization và Triton dynamic batching sẽ dễ hiểu hơn nhiều.
